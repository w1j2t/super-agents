# 87 CLI 客户端：从"只能起服务"到"能自己用起来"

> 一句话：**接这套系统的人第一件事一定是想"提交个任务看看"，而此前唯一的办法是手搓 curl。**
> 这份文档记 CLI 的设计口径、令牌自愈机制、显示契约，以及两处"看起来能跑、实际会咬人"的坑。

## 1. 为什么要有 CLI

在此之前的交互路径只有两条：起服务（`super-agents.exe` 无参）和用 curl 拼 JSON。
第二件事对使用者本人极不友好——每次都要手抄 access_token、手算 UUID、手对 202/201 两种返回。
更麻烦的是 **curl 的失败样子和成功样子太像**：401 也吐一段 JSON，`--json` 不看状态码就会误判成功。

CLI 补的是这一段：把"我要提交一个任务，然后看它跑到哪了"压成两条命令，并且
**在失败时必须用退出码说话**，而不是靠人读输出猜。

## 2. 七个入口

| 子命令 | 别名 | 要不要服务在跑 | 干什么 |
| --- | --- | --- | --- |
| （无子命令） | — | 是（它就是服务） | 启动 HTTP 后端，读 `SA_*` 环境变量 |
| `serve` | — | 是 | 同上，显式写法。**无参启动必须继续等价于它** |
| `doctor` | — | **否** | 只读自检，服务起不来时也能跑 |
| `login` | — | 是 | 登录并把令牌存到本地 |
| `logout` | — | **否** | 删掉本地令牌文件（不动服务端会话） |
| `submit <goal>` | — | 是 | 提交任务，字段与 `POST /api/v1/tasks` 一一对应；加 `--follow` 则提交后逐帧跟到终态（见 2.2） |
| `ls` | `list` | 是 | 列出任务（默认第一页） |
| `show <id>` | `get` | 是 | 看单个任务详情 |

代码分布：`src/cli/` 共 6 个文件约 1570 行——`mod.rs`（参数面）、`doctor.rs`（自检）、
`session.rs`（端点与令牌）、`auth.rs`（登录）、`http.rs`（最小 HTTP 收发）、`task.rs`（业务与渲染）。

### 2.1 无参启动仍是服务（这条是硬约定）

前 22 道门禁里有 20 余处调用形如 `python scripts/xxx.py <exe>` ——**一律无参启动服务**。
所以"没有子命令 = serve"不是一个便利设计，而是整套验收体系的隐含前提。
一旦它被改成"打印帮助并退出 0"，**二十道门禁会集体变红**，而每道报告只会说"服务起不来"，
排查的人会从"服务坏了"这个完全错误的方向重新读一遍 `main.rs`。

门禁 22 把它单独钉成一条断言：无参启动后 `/healthz` 必须 200、进程必须留在前台、
退出后端口必须释放；同时**拼错的子命令必须被拒绝**，不许静默回落到 serve——
否则 `super-agents docotr` 会静默起一个服务，占用端口八小时。

### 2.2 `submit --follow`：提交完别让我再敲 `show`

`submit` 默认走 async：服务端回 202 + 任务 id，然后**人就断了线索**。
以前的做法是记住 id、隔几秒敲一次 `show`，肉眼判断有没有到终态。这条路有三个毛病：

1. **会漏帧**。sim runner 跑到终态可能只要几十毫秒，`show` 拿的是"当前快照"，
   中间 `running` 那一帧永远看不到——于是"任务是否真的推进过"无法从观测上证明。
2. **会误判**。快照里 `failed` 和 `running` 都只是一行文本，脚本化时得自己再解析、再翻译退出码。
3. **不知道停在哪**。轮询被 Ctrl+C 打断时，人不知道自己漏了哪几帧。

`--follow` 把这段补上：提交成功后直接订阅 `GET /api/v1/tasks/{id}/events`，
逐帧打印，**看到终态才退出**，退出码由终态翻译。

| 观察到 | 退出码 | 输出 |
| --- | --- | --- |
| 终态 `succeeded` | 0 | 逐帧 `[seq] 帧`，末帧为终态 |
| 终态 `failed` / `aborted_budget` / `cancelled` | 2 | 同上，末帧标出真实终态与原因 |
| 事件流在终态前断掉 | 2 | 明说"终态之前就结束了（最后 seq=N，坏帧 M 条）" |
| 二次 401（刷新后仍无权限） | 3 | 要求重新 `login` |
| `--budget-*` 被服务端 422 直接拒 | 2 | 原样吐出服务端拒绝理由 |

四条设计口径，都是"宁可难看，不可假装"：

- **同步任务不装样子**。`--mode sync` 时服务端一次返回 200/201，本就没有中间态可跟。
  此时输出"本次同步完成（HTTP 201），没有中间进度可跟；想边跑边看请加 `--mode async`"，
  并且**不打印任何帧**——静默返回 0 会让人以为"跟完了、一切正常"，实际什么都没跟。
- **断线不重连**。SSE 断了就是断了，重连只能重放快照，拼出来的时间线是假的。
  与其给一条平滑但失真的线，不如明说断在第几帧。
- **401 只自愈一次**。复用会话层的 `refresh`，二次仍 401 直接 `RC_AUTH`，避免刷新环。
- **`--json` 每行一个完整 JSON**。帧要能 `jq -c` 逐行吃，混进一行人类提示就把管道断了。

真机证据（本机 exe，非模拟）：正常任务帧序列 `[0] running` → `[3] running` → `[4] succeeded`，rc=0；
把预算压到 200/400/800/1500 后，四个档位全部落在 `aborted_budget` 且 rc=2——
证明"非成功终态 → 非 0 退出"这条翻译不是空壳。门禁 23 的 F 组把上述行为钉成 6 项断言，
其中 F3 专抓"重连拿快照拼时间线"（要求帧序号严格递增），F5 专抓"同步任务假装跟随"。

> 顺带记一次自己的错：F5 首版的目标句写成"写一句话说明 tcp 与 udp 的区别"，
> 被服务端以 422 拒在门口（该句未命中任何类型关键词），红色落在门禁上却与 follow 无关。
> 用例设计错和被测对象错长得一模一样，只有把 goal 换回可识别类型（"总结"→writing）才分得清。

## 3. 连接与令牌

### 3.1 地址只有一个来源

刻意**不提供** `--base-url` 这种"整条 URL"参数：CLI 只连本机这台服务，
让人填 scheme 只会多一种出错方式（`http://` 拼两遍、末尾多一个 `/`）。

取值优先级：`--addr` → `SA_BIND` → `127.0.0.1:8088`。
写 `http://127.0.0.1:8088` 也认（复制粘贴 URL 的人不管有没有 scheme），
程序会剥掉 scheme 与尾斜杠——但**默认值和服务端 `Config` 保持一致**，不会出现
"服务起在 `SA_BIND` 上、CLI 却连默认端口"这种错位。

### 3.2 令牌文件

| 项 | 规则 |
| --- | --- |
| 位置 | `SA_TOKEN_FILE`；缺省 `SA_DATA_DIR/cli-token`，再缺省 `data/cli-token` |
| 格式 | 两行明文 `access=…` / `refresh=…`（`refresh` 可能没有） |
| 写入 | 先写临时文件再 `rename` 落盘，避免半截文件 |
| 取值优先级 | `--token` → `SA_TOKEN` → 本地令牌文件 |
| 打印 | `login` 只报"登录成功 + 有效期"，**默认不回显令牌**；要原值用 `--show-token` |

默认不回显不是洁癖：门禁与演练的证据会整段落进 `docs/evidence/`，
一旦把 access_token 打进标准输出，它就会永久留在证据文件里。

### 3.3 客户端不复用服务端的 `Config`

`Endpoint` 只取两项：地址、令牌文件。**刻意不走 `Config::from_env()`**——那是服务端的完整校验
（JWT 密钥 ≥32 字符、槽位枚举合法性……）。若 CLI 也走它，用户为了执行一条 `ls`
就得在客户端环境里配好 `SA_JWT_SECRET`，而这对一个只读命令毫无意义。
服务端该校验的东西，交给 `doctor` 在服务端那一侧校验。

## 4. 401 自愈：一条真缺陷的完整来路

服务端的 refresh 是**轮换 + 重放检测**：每用一次 refresh 换一对新令牌，旧的立刻作废；
拿旧 refresh 再来一次，会被当成重放攻击直接 401。

CLI 侧的期待行为是：access 过期 → 用 refresh 换新 → 重试原请求 → 把新令牌写回文件。

**第一版就错在这里**，而且错法极隐蔽：

```text
access 链的取值：v["access_token"] 或 v["tokens"]["access_token"]
refresh 链的取值：v["new_rtok"]   或 v["refresh_token"]      ← 漏了 tokens 一层
```

服务端返回的是 `{ "tokens": { "access_token": …, "refresh_token": … } }`。于是 refresh 链
只能靠 `old.refresh` 兜底——**把刚被服务端作废的旧 refresh 又写回了文件**。
后果是：命令 A 成功，命令 B 必 401，命令 C 又好了（因为它读了新写的坏值……有时又好）。
人工点几下根本发现不了，因为"再执行一次就好了"。

修法只有一句注释能表达清楚：**两条链必须同样宽**。

```rust
let pick = |k: &str| v.get(k).or_else(|| v.get("tokens").and_then(|t| t.get(k)));
```

### 4.1 并发刷新：8 个进程同时 401 怎么办

单进程修好之后仍有竞态：8 个 `ls` 同时发现 access 过期，8 个都去 refresh，
轮换语义下**只有一个能成**，其余七个拿着已作废的 refresh 必然 401。

处理方式落在**失败方**：重试前先重读一次本地令牌文件，看有没有对端刚写好的新值。

| 重读结果 | 处理 | 提示 |
| --- | --- | --- |
| `Rescued`：文件里已是新令牌 | 直接用新令牌重试 | 不打扰用户 |
| `WaitedButStillOld`：退避 8 次 × 60ms 仍是旧值 | 失败退出 | "再执行一次" |
| `Hopeless`：连 refresh 都没有 | 失败退出 | 要求重新 `login` |

第一版只做"读一次比对"，实测 6 并发 × 3 轮里有一半 `rc=3`——失败方重读时，成功方还没写完。
加上退避重读后才全绿：**6 并发 × 3 轮、12 并发 × 5 轮 `codes` 全 0**，
令牌文件完整，并发结束后单跑 rc=0。

## 5. `doctor`：服务起不来时唯一能用的东西

`doctor` 的定位是"**服务起不来时也能跑**"，所以它**不复用 `AppState::new()`**——
否则"服务起不来"会连带把诊断器一起弄死，而诊断器恰恰是此刻唯一有用的工具。

十项检查，顺序固定（先环境、后资源、最后外联）：

| # | 检查项 | 判据 |
| --- | --- | --- |
| 1 | 配置加载 | `Config::from_env()` 能否成功；失败时其余项统一记 SKIP |
| 2–6 | 数据 / 审计 / 限流 / 指标 / 执行五个槽位 | 目录可写、执行槽位所需的 `SA_RUNNER_DIR` 是否存在 |
| 7 | 监听端口 | 三分：`Free` / `Ours(code)` / `Foreign` |
| 8 | 模型端点 | `SA_LLM_BASE` 半配（只配一半）必须报 ERR |
| 9 | 集群心跳 | 心跳目录可写；`SA_CLUSTER=off` 时不检 |

配置加载失败时，其余九项**统一记 SKIP 而不是 OK**——这是刻意的：
诊断器最坏的失败不是报错，是**产出一个"看起来还好"的假象**。

端口三分里 `Ours` 值得单说：bind 失败不等于端口被占，可能是**本服务已经在跑**。
判法是真去请求 `/healthz`，200 就是自己人，文案写"已有本服务在跑"；
否则才是"端口已占用且不响应 HTTP"。

### 5.1 退出码即判据

| 码 | 含义 |
| --- | --- |
| 0 | 全通过（`SKIP` 不算失败） |
| 1 | 有 WARN，且给了 `--strict` |
| 2 | 有 ERR |

`--json` 输出 `{version, exit_code, checks[], summary{total,ok,warn,skip,error}}`，
`checks` 的**名单与顺序必须与文本模式逐项一致**，`level` 取值封闭在 `OK/WARN/SKIP/ERR` 四值。
门禁 22 的 C 组就是拿"文本汇总行 ↔ JSON summary"同数同码来判的——
一个只会打印漂亮表格、JSON 里对不上号的诊断器，等于没有机器契约。

## 6. 显示契约：三个"看起来正常"的坑

真起服务跑一遍全链路，抓到五个显示问题，其中三个有代表性：

### 6.1 按字符数补空格 → UUID 被截断

表格原先按 `len()` 补空格。中文字符在终端占**两列**，按字符数算就会少补，
于是 `id` 列只留出 20 列，UUID 被截成 `204750aa-…?`——**无法复制去 `show`**。
同批 `tokens` 列被截成 `12936/15…`。

修法：`pad` / `trunc` 全部按**显示宽度**算（`dwidth`：宽字符计 2）。
`id` 列宽 20 → 36，`tokens` 9 → 13，状态 16 → 19，类型 11 → 13，时间新增 19。

### 6.2 时间是 UTC，列头却只写"创建时间"

服务端存 UTC，这是对的；错的是**只写"创建时间"**——本地 15:00 看到 `07:00` 会以为任务挂了。
现在列头写 `创建时间(UTC)`，详情页的 `创建/更新/完成` 三项也各带 `(UTC)`，页脚追加"；时间为 UTC"。

### 6.3 中文字段在 PowerShell 里是乱码

exe 输出 UTF-8，而 PowerShell 5.1 按 GBK 解，`--json` 直接无法 `json.loads`。
这不是程序错，是取法错：读子进程输出必须**收字节再显式 `utf-8` 解码**。
门禁 23 的 D 组因此加了一条"输出里不得出现 `\ufffd` 替换符"——乱码在字符串层面就是这个字符。

### 6.4 顺带一条：列位取值最容易写成恒绿

门禁 23 的 D 组要按列位切表格。格式串是 `"{} {} {} {} {} {}"`，**列间还有一个分隔空格**，
所以第 `i` 列的起始偏移是 `sum(COL_WIDTHS[:i]) + i`，不是 `sum(COL_WIDTHS[:i])`。
少算这一个偏移，取到的就是"上一列的尾巴 + 下一列的开头"——时间列切出 `2026-11-14 07:3`、
完整 UUID 只数到 1 个字符。这类断言会在**看起来有值**的情况下恒绿，因此按列位取值必须
配一次负向演练（`--drill` 换 `where.exe` 后被 57 项成片判红）。

## 7. 两道门禁

| 门禁 | 脚本 | 守什么 | 规模 |
| --- | --- | --- | --- |
| 22 | `probe_cli.py` | **外壳**：无参=serve、未知子命令被拒、`--help`/`--version`、doctor 退出码三分、端口释放 | 22 项，约 5s，进 quick 层 |
| 23 | `probe_cli_http.py` | **客户端**：登录落盘与覆盖、401→刷新→重试并回写、8 进程并发自愈、显示宽度对齐、UTC 标签、`--json` 纯净、连不上必须 rc=1、**`--follow` 逐帧到终态** | 57 项，约 16s，只进 full 层 |

两道分开的原因是排查方向不同：22 红了说明**外壳或默认语义变了**，
23 红了说明**客户端与服务的握手变了**。合成一道，报错时就分不清是哪一头。

两道的 `--drill` 都是把被测物换成 `C:\Windows\System32\where.exe`——一个"完全不像本程序"的东西。
门禁 22 演练 10 项全红，门禁 23 演练 57 项全红（A~F 组），附 `[DRILL-OK]` 自证行。

### 7.1 演练行不能沿用门禁的摘要口径

`regress_all.py` 里门禁与演练原本共用 `tail_lines()`（关键词含"通过"）。演练的 rc=0 表示
**成片变红**，而"通过"两个字恰好出现在 `2/12通过` 这种明细里——于是演练行抽到的全是 `[FAIL] …`，
真正的结论行 `[DRILL-OK] … 说明判据有判定力` 一个关键词都不沾。

实测后果：rc=0、演练 5/5 按预期的一轮，报告里整段写着 `FAIL market …` / `FAIL A3 …`，
读的人第一反应是"门禁失去判定力了"，去查一个不存在的缺陷。**证据里结论被明细淹没，比没有结论更坏**。

现在分成两套：`drill_tail()` 只抽 `DRILL_KEYS`（`DRILL-OK` / `演练按预期` / `按预期变红` / `未达预期`），
`run(..., drill=True)` 的 status 写 `DRILL-OK` / `DRILL-FAIL`（不写 PASS——演练的"成功"含义与门禁相反），
每行前面加判定语"按预期变红 / 未按预期"。没有自证行的纯 rc 型演练（`drill-openapi6.py`）退回普通摘要。

### 7.2 `--fast` 的口径（第一版写错了）

`--fast` 最初跳过 B/C 两整组，结果 D 组因为"没登录"整片变红——**门禁自己被快档跑成了假红**。
现在 `--fast` 只砍并发那一项（C10），其余照跑：51/51。

## 8. 取舍与未做

| 项 | 现状 | 为什么 |
| --- | --- | --- |
| 令牌明文落盘 | `data/cli-token`，两行明文 | 个人单机、当前用户目录权限即是边界。上多用户机时应换 OS 凭据库，属换件范畴 |
| `logout` 不动服务端会话 | 只删本地文件 | 无状态 JWT，服务端注销要靠黑名单；为一个换账号动作引入黑名单表不划算 |
| 无交互式 TUI | 无 | 目标是"能进脚本、能进门禁"，TUI 与这个目标相反 |
| 未做 `submit` 后的自动跟随 | 需手动 `ls`/`show` | SSE 已有 `Last-Event-ID` 续传能力（门禁 17），跟随进度是下一步很自然的一步 |
| 未做薄封装子命令 `submit`/`ls`/`show` 之外的业务动作（如 `cancel`） | 无 | 复用 API 同源语义、不新增业务规则；要做也只在客户端，不动服务端判据 |

## 9. 一条给后来者的经验

CLI 是这套系统里**唯一一层面向前台的代码**，而前台的错法有个共同特征：
**看起来都正常**。UUID 被截断、时间差八小时、`--json` 里混了乱码、401 后"再执行一次就好了"——
这些都不会让任何一道既有门禁变红，也不会在人工点几下时暴露。

所以这一层的验收不能只看"命令能跑通"，必须逐项断言**形状**（显示宽度、字段完整、UTC 标签）
和**退出码**（连不上必须 rc=1，不许崩栈）。这也是门禁 23 全篇的主线：
它测的不是功能有没有，而是**出错时说不说得清**。
