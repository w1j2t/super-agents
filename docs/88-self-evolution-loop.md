# 88 · 自进化闭环：让实测反过来驱动项目自身

> 一句话：**用本地小模型当探针，用真实长跑当显微镜，由主 Agent 负责修，再用同一把尺子量回来。**
> 探针不是作者。模型只负责"把系统逼出错"，改代码的是人（这里是主 Agent），判定改得对不对的是数据。

这份文档回答四件事：闭环怎么转、凭什么说"变好了"、第一代真修了什么、以及怎么防止自己骗自己。

---

## 1. 先把定义钉死

"自进化"在这个项目里有严格含义，三条边界，越界就不算：

| 边界 | 允许 | 禁止 |
| --- | --- | --- |
| 谁来找问题 | 本地 2B 模型反复跑真实任务，把系统的边界撞出来 | 让本地模型"自己改项目"——它连 Rust 都写不利索 |
| 谁来修 | 主 Agent 读证据、定位、改代码、写回归 | 靠"调大超时/加重试"把指标刷上去 |
| 谁判输赢 | 固定尺子（同一批任务、同一套判分）前后测量 | 换题、换尺、换口径之后再说"变好了" |

一句话概括：**进化的是项目，不是模型。** 模型在这里相当于一个"不知疲倦但能力很弱的测试员"，它的价值不在产出，而在**稳定地把系统的薄弱处暴露成可计数的失败**。

---

## 2. 闭环怎么转：五段式

```
   ① 观测          ② 分桶            ③ 假设            ④ 修复           ⑤ 判定
真实长跑 N 轮 → 失败归因成桶 → 挑最大桶问"为什么" → 改代码 → 证据留存 → 同尺重测 → 代际比较
     ↑                                                                              │
     └────────────────────────── 不过就继续下一圈 ←────────────────────────────────┘
```

每一段都有对应的硬要求，缺一段闭环就断：

1. **观测**：必须是真起进程、真打 HTTP、真落 jsonl。判断"这轮算不算完成"不能靠肉眼，要有可在事后复核的字段。
2. **分桶**：失败必须归到**不同根因**的桶里。`status=failed` 这种粒度等于没归因——`timeout-no-output`、`no-code-at-all`、`syntax-error`、`unverified` 各自指向完全不同的修法。
3. **假设**：只挑**最大且最可疑**的那个桶动手。同时改三处，之后涨了也不知道是谁的功劳。
4. **修复**：改动要能被单独回滚，且必须写清"为什么这么改"（注释里写下踩过的坑，比写"优化"有用一百倍）。
5. **判定**：换一把新尺子量出来的结果**不能**和旧尺子的数据混在一张表里比。要么同尺重测，要么把旧数据按新逻辑重放（这就是 §5.3 要的证据留存）。

## 3. 度量三件套：谁负责什么

三件工具职责不重叠，缺一件就有一类问题看不见。

| 工具 | 位置 | 只干一件事 | 缺了会怎样 |
| --- | --- | --- | --- |
| `soak_project.py` | `scripts/` | **产生**数据：起服务、发任务、抽代码、判语法、落 jsonl | 没有真实样本，一切讨论都是猜 |
| `soak_campaign.py` | `scripts/` | **汇总**数据：多批次合并、按语言/项目/阶段/代次分层 | 只能看单批，看不出"第 N 代是否更好" |
| `evolve.py` | `scripts/` | **判定**数据：失败分桶、Wilson 区间、代际判据、判分重放 | 会把噪声当进步，把退步当运气 |

三者的关系是：`soak_project` 产粮食，`soak_campaign` 记账，`evolve` 做裁判。裁判不能自己种粮，否则一定偏心。

## 4. 凭什么说"变好了"：Wilson 区间，不是点估计

### 4.1 一个真实的反例

早前跑过一批 100 轮：达交付 62%。更早一批 148 轮去重后：45.9%。
看上去是"大幅提升 16 个百分点"，很容易顺手写进报告庆祝一下。

但样本只有几十上百，这两个数的 95% 置信区间是重叠的。`evolve.py` 遇到这种情形只会输出 **"未见显著差异"**，不给"改善"两个字。这不是保守，是**诚实**：在 100 样本量上，62% 与 45% 完全可能来自同一个真实水平。

### 4.2 判定规则（写进代码，不靠自觉）

`judge_gen()` 三层，任一不过就不算进化：

1. **样本层**：本代 ≥ 100 轮且覆盖 ≥ 2 个项目，否则直接拒绝参与比较（输出"样本不足"，不是"通过"）。
2. **质量层**：达交付率、编译通过率、完成率三项，比较 **置信区间**；出现"退化"即否决。
3. **成本层**：单位交付 token 上涨超过 20% 判为退化——靠烧更多 token、堆更多重试换来的交付率，是假进化。

结论只有四种：`通过` / `未通过（有指标退化）` / `待定（无显著变化）` / `首代（无基线）`。
**"待定"是常态**，它的意思是"还没攒够证据"，不是"没做好"。

## 5. 第一代：真修了什么（有数为证）

第一代动手前，池子里有 145 轮真实样本（去重后），状态如下：

| 指标 | 数值 |
| --- | --- |
| 样本 | 145 轮 |
| 任务完成 | 140（96.6%） |
| 达交付标准 | 82（56.6%） |
| 编译通过 | 84 / 145（旧口径，含假红，见 5.2） |

失败归因大体如下（`evolve.py --buckets` 真实输出）：

| 原因 | 轮数 | 占比 | 语言分布 | 下一刀该切哪 |
| --- | --- | --- | --- | --- |
| `syntax-error` | 36 | 24.8% | python 28 / rust 8 | 代码抽出来了但不合法，查抽取是否截断 |
| `no-code-at-all` | 19 | 13.1% | none 16 / rust 3 | 一句没写，区分提示词还是能力 |
| `timeout-no-output` | 5 | 3.4% | none 5 | 查超时与后端吞吐 |
| `not-delivered` | 3 | 2.1% | python 3 | 查判定阈值 |

第一代挑了三处动手，按"危害排序"而不是"好改排序"。

> **补记（同日晚）**：修完前三处立刻用 `--rejudge` 重放，结果翻出 48 条翻案、35 条假绿（详见 5.4），
> 于是又补了三处（5.4–5.6）。**"第一代"最终是六处，不是三处——而多出来的三处，全是前三处复算后才暴露的。**
> 上表中的 `syntax-error 36 条 / 24.8%` 是**旧尺的判决**；新尺下该桶只剩 11 条，
> 真正的第一大桶是 `placeholder-instead-of-code` 48 条。这张表保留原样，作为"旧尺曾经误导我们"的存证。

### 5.1 修一：任务流从头就撞墙（危害：整批数据作废）

**现象**：两次启动长跑（1000 轮 / 600 轮），第 1 轮就是 `st=None agents=0 code=- 600s`，jsonl 只有几行。

**定位**：`build_goals` 按 `PROJECTS` 原序轮转，而 P1–P6 **全是 Rust**。2B 模型在 Rust 上必然吃满 `--task-timeout 600s`，于是长跑开局即卡死——前面几百轮全白烧，还占着 CPU。

**修复**：`build_goals(..., order="easy-first")`，按语言把模型更可能完成的 Python 侧项目排到前面；`--order legacy` 保留原序用于对齐历史批次。

**验证**：`build_goals(6)` → `P5/P5/P5/P6/P6/P6`；`--order legacy` → `P1/P1/P1/P1`。

**为什么这么修而不是"把超时调大"**：调大超时是掩盖。真实情况是"Rust 任务在当前模型下不可完成"，这一类必须作为**能力上限**被单独度量（所以 `--suite rs` 单列），不能混进主线把完成率拉到地板上。

### 5.2 修二：判分器把"没证据"当成"有结论"（危害：指标被系统性污染）

**现象**：47 条编译失败里，34 条的 `compile_detail` 是同一句——"worker 自检（output 被平台截断，本机无法复验）"。

**根因**：判分代码写的是 `ok = bool(mark_deliv)`。`mark_deliv` 是 worker **自报"已交付"**，语义与"代码能编译"完全不同。两个字段一混，编译列就变成一锅粥，而且方向还会随 worker 自报乱翻——一会儿假红、一会儿假绿。

**修复**：编译判定改**三态**：
- `True` 本机实测通过；
- `False` 本机实测失败；
- `None` 无法验证（无完整代码 / 缺 rustc），**不进入编译率分母**。

同时把 worker 自报值单列成 `worker_claim_delivered`，只作对照，不参与编译结论。失败归因也新增 `unverified` 桶。

**为什么必须三态**：二态的表达力不够时，人会本能地把"不知道"塞进"否"里。这在报表上看起来只是数字低了一点，实际后果是**修错方向**——你会去查模型的代码质量，而真凶是观测链路。

### 5.3 修三：判分自身不可复现（危害：改判分就要重跑几小时）

**现象**：想"拿旧数据按新判分逻辑重算"，发现做不到——落盘时每个 step 只留了 `out[:160]`（给人看的摘要），判分时用的 `out_full` 根本没存。

**根因**：只想着"证据够复盘"，没想着"证据要够重算"。这两件事的粒度差一个数量级。

**修复**：新增 `judge_evidence`，随每条样本落盘：

| 字段 | 作用 |
| --- | --- |
| `code_full` | 被判分的代码本体（超 4000 字符保留头尾并标 `code_truncated`） |
| `code_sha1` / `joined_sha1` | 事后核验"这段证据有没有被改过" |
| `marked` | 当轮用的标记值（delivered / lang / chars） |

配套 `evolve.py --rejudge`：用留存证据按**当前**逻辑重算编译结论，输出"哪些样本结论变了、往哪个方向变"。老批次没留证据的会明确报"不可重放"，**绝不猜**。

**这一条的意义**：它把"改判分器"从"几小时重跑"降级为"分钟级重算"。判分器也是代码，也会写错；不给它留重放通道，就等于把判分器钉死成不可修。

### 5.4 修四：抽取器把"没写代码"当成"代码编译通过"（危害：35 条假绿，指标被抬高）

**现象**：`--rejudge` 重放 233 条有证据的样本，48 条翻案。其中 **35 条从 `True` 翻成 `None`**，抽出来的"代码"原文是：

```
...
```

三个点。而 Python 里 `...` 是合法的 **Ellipsis 表达式**，`compile("...")` 返回成功。于是"模型啥也没写"被判成"代码编译通过"。另 13 条是 `<code here>` / `<你的代码>`，被判成语法错。

**根因**：判分逻辑只看"编译是否成功"，却没问"**喂给编译器的东西是不是代码**"。锚点上系的是抽取器的输出，抽取器抽错了，锚点就是假的——但它仍然会给出自信的成功。

**修复**（三道闸，缺一不可）：

| 闸 | 做法 |
| --- | --- |
| 结构探测 | `_STRUCT_RE` 从裸 `[=;]` 收紧为 `\w\s*\(|=`，避免 `print("hello")` 这类合法短代码被误判 |
| 占位符识别 | 命中 `<code here>`、`<你的代码>`、`(your full code here)`、裸 `...`、`TODO`、空串 → `compiles = None` + `compile_source = "placeholder"` |
| 语言猜错 | 围栏语言与内容不符 → `compiles = None` + `compile_source = "lang-guessed"`，不让它冒充编译失败 |

配套：`--selftest` 增第 4b 节，**正负样本都要有**——正样本 6 条、负样本 5 条。只测正样本时，`return True` 也能全绿。

**这一条的意义**：假红会让数字难看，人不爽，于是去查；**假绿会让数字好看，人满意，于是什么都不会发生**。35 条假绿静悄悄躺了很多轮，一直在替"编译通过率"抬轿子。

同时它也证明：**假红与假绿同源**。两者根因都不是编译逻辑，而是"抽取错了东西"。修一个判据，两个方向同时收敛——`syntax-error` 桶从 56 条降到 11 条，`placeholder` 桶从 0 变成 48 条。

### 5.5 修五：编译率的分母混进了"永远不可能通过"的轮（危害：指标系统性偏低）

**现象**：报表打"275/410"，但 410 里有 86 轮压根没产出代码（`no-code-at-all` 等），它们永远不可能算通过，却被算进了分母。

**根因**：`metrics()` 里 `compiles_pct` 的分母用的是 `judged`（非 `None` 的条数，正确），但 `show_buckets` 打印时手滑传了 `m["n"]`（总样本数）。代码对，打印错——**这种错最难发现，因为逻辑层测试是全绿的**。

**修复**：

1. `metrics()` 增 `judged`、`compiles_verifiable`、`judged_verifiable`、`compiles_verifiable_pct`、`compiles_verifiable_ci`；
2. `show_buckets` 打两行——主行分母只含可判定轮，次行为**可复验子集**（证据在手、能被当前尺子复算）；
3. `judge_gen` 的跨代比较改用 `compiles_verifiable_ci`；
4. `_cmp_rate` 加 `alias` 回落：旧基线没有新键时回落旧键并在指标名后缀「（基线口径=…）」，两边都缺则判 `不可比`——**不许因为缺键把判据链打断**。

**这一条的意义**：指标的分母就是它的诚实度。分母里混进"注定失败"的样本，等于让系统永远看起来比实际差一点；混进"无法验证"的样本，等于让假绿永远有地方躲。

### 5.6 修六：改了尺子，历史结论必须自动跟着改

**现象**：`load_samples` 读历史样本时直接用落盘的 `compiles` 字段——那是**当年那把尺子**的结论。修了四次判据，报表却还在用第一把尺子的判决。

**修复**：`load_samples` 末尾统一 `return apply_current_judge(rows)`。对有完整证据的样本，按**当前**逻辑重算，同时：

- `compiles_original` 保留旧值（可追溯"翻案前是什么样"）；
- `compile_source` 记 `local-recalc`；
- 清空旧 `failure_reason`，交给 `reason_of` 按新口径重推。

无证据的老批次原样保留，并在桶里明确标 `legacy-unverified`（33 条），**不参与决策，也不假装参与**。

配套修 `rejudge` 的对照基准：`old` 必须从 `compiles_original` 取，否则 `load_samples` 已重算过，新旧值恒等，重放结论永远是"0 条变化"——**一个永远返回"没问题"的检查器，比没有检查器更糟**。

**这一条的意义**：尺子改了，历史必须重判，否则每一代都在用不同的尺子量，代际比较全是假的。而"能重判"的前提，正是 5.3 那条证据留存。

## 6. 反假进化条款（防自己骗自己）

这几条是硬约束，写在 `evolve.py` 里而不是写在文档里，因为写在文档里的规则最容易被"这一次特殊"绕过去。

1. **不许换尺**：改判分逻辑后，必须 `--rejudge` 重放旧数据，或整批重测；新旧口径禁止混在一张表里比较。
2. **不许合并口径**：`unverified`、`timeout`、`syntax-error` 三类失败不能合成一个"失败率"再吹嘘下降。
3. **不许只看均值**：交付率必须带置信区间；耗时必须给 P50 + P95（P95 才是用户真正会撞见的那一次）。
4. **不许单点样本**：样本 < 100 轮或只覆盖 1 个项目的代次，只能记档，不能进判定。
5. **不许成本失控**：单位交付 token 上涨 > 20% 直接判退化，哪怕交付率涨了。
6. **不许把"待定"说成"成功"**：无显著变化就是无显著变化。

## 8. 并发拐点的实测记录（顺带撞出来的第四个坑）

计划是 4 个进程并行各 250 轮，凑够千轮。实测结果：

| 路数 | 第 1 轮表现 |
| --- | --- |
| 4 路并行 | 2 路成功（97s / 575s），2 路吃满 600s 超时 |
| 2 路并行 | 均正常出轮次（456s / 595s） |

本机是 CPU 推理（`nvidia-smi` 不存在），单发约 5 tok/s，算力是硬上限。**并发数不是越高越好，拐点在 2 路附近**，再多只是把超时率堆上去。

这一条暂时没有代码化（没有做自适应并发控制），先记为已知边界：`--rounds` 与进程数要匹配这台机器的推理吞吐，否则 600s 的 `task-timeout` 会把"慢"记成"失败"。

  | 症状 | `syntax-error` 28 条 Python | 模型不写代码，只吐 `<code here>` / `...` / `<你的代码>` |

  | 改法 | 调代码格式约束 | 硬性禁止占位符 + 给正反例 + 命中即判失败重来 |

  旧靶心里"`max-tokens` 截断"这个怀疑已被证据打消——48 条占位符样本的 `code_full` 都是**极短文本**（最长 3 字符），不存在截断。`syntax-error` 现在只剩 11 条（rust 8 / python 3），已不是主要矛盾。

  定位方式：`python scripts/evolve.py --buckets` 看桶，再读 `judge_evidence.code_full` 直看原文。

## 10. 这份文档的立场

工程上最容易发生的不是"做不出来"，而是"做出来了但自己不知道做得好不好"。上面六个修复里，有四个（5.2、5.3、5.5、5.6）都不是功能缺陷，而是**度量缺陷**——它们不会让程序崩溃，只会让判断失真。而失真比崩溃更难发现，因为它一直"看起来正常"。

更值得记住的是它们的**暴露顺序**：前三个是"看数据看出来的"，后三个是"重放复算翻出来的"。如果不做 5.3 的证据留存，5.4 那 35 条假绿永远不会现身——**你不会发现一个你没有能力复查的错误**。

自进化循环真正的产出，不是某一版更好的代码，而是**一把握得住、能量得准的尺子**。尺子稳了，后面每一条设计方向（见 `89-agent-design-trends.md`）才有讨论的基础。
