# 83 · worker 分词质量：从"能用"到"不出脏词"

> **一句话**：`workers/_common.py` 是 9 个 worker 共用的文字地基——`doc-agent` 的**文档标题**就是它的
> `topic()`，**关键词**就是它的 `keywords()`。这一轮把它的 9 类切词缺陷一次性修完，
> 25 条真实业务目标在**同一判据**下从 17 条通过变成 **25/25**，脏词问题条目 **12 → 0**，
> 并固化为 `regress_all.py` 的第 17 道门禁（编号 16）。
>
> 证据：[`evidence/token-polish-latest.txt`](evidence/token-polish-latest.txt)
> 复现：`python scripts\probe_worker_text.py --verbose`
> 回滚：`temp\_common.py.before-token-polish`（sha1 前缀 `067258836839e7bd`）

## 1. 这个功能要回答的三个问题

| 问题 | 对应函数 | 如果不答会怎样 |
|---|---|---|
| 用户的目标里，哪些是**真词**？ | `tokens()` / `keywords()` | 检索、要点标题、路由全建在噪声上；真词丢了，下游再准也没用 |
| 这份文档该叫什么？ | `topic()` | 整句原样回显（"对比 2B 与 14B 模型在本机 CPU 上的耗时"当标题），或带标点尾巴 |
| 换了融合多家意见的 4 字组合，是词还是两块碎片粘一起？ | `_runs()` 的整段收录 | "订单表加"、"字段名要"、"先搭地形"这类粘连直接进产物，人一眼看出是机器拼的 |

一句话：**这不是"分词准不准"的学术问题，是"交付物里会不会露馅"的产品问题。**

## 2. 边界先划清（明确不做什么）

| 做了什么 | 没做什么 | 为什么不做 |
|---|---|---|
| 词表 + 规则 + 停用词，纯 Python，零依赖 | 引入 jieba / pkuseg / 任何 NLP 库 | worker 是**被主程序按需拉起的外部进程**，加一个带模型的依赖等于给部署加一份体积与启动时间；当前词表 368 词、停用词 132 条已够覆盖业务语境 |
| 用**自研探针**把缺陷固化为 25 条可复跑用例 | 只改代码、靠人肉读产出文档确认 | 历史上这些缺陷就是"人肉读文档才发现的"，没有探针就等于没有防线 |
| 词表保持**通用业务词**（工具/机器/中文/显存/排障…） | 把项目专名（如"修仙""万炉"）塞进词表 | `_common.py` 是公共地基，塞专名会污染所有 worker；专名该走任务上下文，不该走词典 |
| 宁可少一个专名，也不出一个碎片 | 追求新词召回率 | 碎片是**明显错误**（人人都看得出），少一个专名只是**不够好**；错误优先级高于不完美 |

## 3. 修了什么：9 类缺陷 + 3 个潜伏坑

### 3.1 三类"看得见"的脏词

| 类型 | 改前真实输出 | 改后 | 根因 |
|---|---|---|---|
| 尾部碎片 | `字以`（来自"800 字**以内**"） | 消失，`中文` 补回 | `_trim_tail` 只剥单字方位词（`里中下内外的`），"以内"被剥成"字以内"→再剥"内"→`字以`。**新增 `_TAIL_SUFFIX` 多字尾缀先剥，再剥单字** |
| 跨词粘连 | `字段名要`、`订单表加`、`先搭地形` | 消失 | `tokens()` 对 ≤4 字的段**无条件整段收录**；"字段名要和源码一致"被"和"切成"字段名要"，4 字直接当词 |
| 动词短语当关键词 | `汇总成`、`上周`、`顺便` | 关键词只剩 `会议 / 周报 / 团队 / 纪要` | `_LEXICON` 里**误收**了 `汇总成 / 落地到 / 讲清楚 / 说明白`——这四个是动词短语，不是名词 |

### 3.2 丢词与排序退化

| 现象 | 例 | 修法 |
|---|---|---|
| 真词从头到尾没进 tokens | `机器`、`中文`、`工具`、`语音` | 补进 `_LEXICON`（此前词表里根本没有这些常用词） |
| 真词被长词挤出前 8 | `游戏` 排在 `修仙游戏`、`先搭地形` 之后 | `keywords()` 按 `(-len, w)` 排序会把 4 字碎片顶到第一；碎片消失后自然归位 |
| 主题整句复读 | 3 条用例 `topic` 输出 20 字以上整句 | `topic()` 加退化兜底：>12 字且含虚字 → 改用锚点词（`_longest_lexeme` 从命中词里取最长名词） |

### 3.3 三个潜伏坑（比上面更值得记）

**坑 1 · `set("长串".split())` 的停用词表从来没生效。**
长串中间没有空格，`.split()` 返回的是**只含一个巨长字符串**的集合，于是 `w in _STOP` 永远为假。
停用词一次都没生效过，连带依赖它做切分的 `_SPLIT_WORDS` 也拿不到任何分隔词——这才是"跨词碎片"的真正源头。
修法：拆成 `_STOP_CHARS`（逐字 set）+ `_STOP_WORDS`（多字词花括号集合），再 `|=` 合成为 `_STOP`。

**坑 2 · 三引号里的 `#` 不是注释。**
`_LEXICON` 是 `"""..."""` 字符串。我在里面写 `# 常用名词`，它不会成为注释，整行说明被 `.split()` 切成词条，
再被 `_lexicon_guard` 当成"合法词"整词认走——探针 25/25 全绿，但真实输出里仍冒出 `在本机的`、`排查高`、`先搭地形`。
**这是本轮最危险的一处**：门禁绿了、产物还是脏的。后来扫出 28 条被污染的"词条"（含 `漏一个就会被`、`的注释）。` 这种半句），
把注释全部移出三引号、改成三段字符串拼接才清干净。含虚字条目 28 → 17，且剩下 17 条都是正常词（主从 / 对应 / 对接 / 并发 / 就绪 / 合并）。
教训：**"探针全绿"不等于"输出干净"——必须人工扫一遍真实输出。**

**坑 3 · 判据本身会把"设计"误判成 bug。**
探针最初要求 must 词**原地出现**在 tokens 里，于是 `试点` 因为被收录成 `试点报告` 就报"丢词"。
这不是 bug，是**长词吸收**（子串去重属设计）。改判据为 `covered(w, bag)`——`w == t or w in t or t in w` 即算覆盖。
因此基线从最初的 `2/25`（严判据）重算为 **`17/25`（同一判据，可比）**。
诚实说明：`2/25 → 25/25` 这个跨度混了判据变化，**不是**同一把尺子；本文只用同尺子的 `17 → 25`。

## 5. 四个"看起来可以更简单"的决定

1. **为什么不直接上 jieba？**
   见 §2。一句话：worker 是外部进程，加依赖等于给每次拉起加启动成本；而当前 368 词已把 25 条真实用例打到 25/25。**能用规则解决就别加依赖**，等词表真的撑不住再换——那时换的理由是数据，不是"这个库更有名"。

2. **为什么 4 字整段要按"两截是否都在词表"判，而不是直接全收或全丢？**
   全收 → 出 `订单表加`；全丢 → 丢 `子文件夹`、`试点报告`（两截都不在/都在，都是真词）。所以判据是**对称的 XOR**：
   两截都命中 → 保留（真组合词）；两截都不命中 → 保留（如 `子文件夹`，交给后面兜底）；**只有一半命中 → 判为粘连丢弃**，命中的那半截由段内扫描补回。
   这个"补回"是关键，否则丢掉粘连的同时会把 `订单` 一起丢掉。

3. **为什么主题宁可短到两个字（`评估`），也不留整句？**
   整句当标题是**明显错误**；`评估` 只是**不够好**。不够好的标题人会自动补，错误标题会让人以为系统坏了。同理，宁可 4 字专名丢掉也不出碎片。

4. **为什么把探针做成门禁 16，而不是留在 temp 里？**
   因为**前 15 道门禁没有一道守"文字处理"**。`_common.py` 退化不会让任何一道变红——它只会让 doc-agent 的要点标题悄悄冒出碎片，历史就是这么发现的：人肉读产出文档。
   凡是"改坏了没人会红"的地方，都不算有防线。

```powershell
python scripts\probe_worker_text.py

# 详细模式：打印每例的 tokens / keywords / topic / 句子切分
python scripts\probe_worker_text.py --verbose

# 机读结果（便于对比两次改动）

# 全量回归（含门禁 16，17 道全绿才算收口）

# 只想快速确认改动没搞坏：快通道（门禁 15 跳过 6×TTL 等待，证据落 evidence/fast/）
python scripts\regress_all.py --fast
```

探针**恒退出 0**（只出数据，不做门禁裁判），门禁 16 才按退出码判定——这样同一个脚本既能当探针调参，又能当门禁守线。

### 6.1 负向演练：证明这道门禁真的会红

一条门禁最怕的不是"没写"，是"写了但永远绿"。所以本轮对门禁 16 做了负向演练：
用 `SA_COMMON_PY` 把**被测文件**指向一份"改前版本"副本，其余一切不变。

| 被测对象 | 退出码 | 通过 | 输出结论 |
|---|---|---|---|
| 改前版本（副本） | **1** | 17 / 25 | `存在真词丢失或脏词，需修 _common.py` |
| 当前正本 | **0** | 25 / 25 | `分词输出无脏词、must 全在` |

`SA_COMMON_PY` 是**只给负向演练用的白名单变量**：不设它，探针永远测项目里的正本；
设了它才能把"假想中的坏版本"喂进来。这样既做了演练，又不需要为演练去动项目文件。
证据：[`evidence/token-polish-negative-drill.txt`](evidence/token-polish-negative-drill.txt)

## 8. 本文档沉淀的三条硬纪律

1. **探针全绿 ≠ 输出干净**：绿了之后必须人工扫一遍真实输出。本轮 28 条词表污染就是这样抓到的——它在门禁眼里完全合法。
2. **判据本身也会错**：改代码前先确认"判据报的是 bug 还是设计"。把设计当 bug 修，会把好功能修坏（`试点`/`试点报告` 一例）。
3. **比较要同尺子**：`2/25 → 25/25` 混了判据变化，不能这么写。换判据就重算基线，再比。
