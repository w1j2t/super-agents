# 88 · 自进化闭环：让实测反过来驱动项目自身

> 一句话：**用本地小模型当探针，用真实长跑当显微镜，由主 Agent 负责修，再用同一把尺子量回来。**
> 探针不是作者。模型只负责"把系统逼出错"，改代码的是人（这里是主 Agent），判定改得对不对的是数据。

这份文档回答四件事：闭环怎么转、凭什么说"变好了"、第一代真修了什么、以及怎么防止自己骗自己。

---

## 1. 先把定义钉死

"自进化"在这个项目里有严格含义，三条边界，越界就不算：

| 边界 | 允许 | 禁止 |
| --- | --- | --- |
| 谁来找问题 | 本地 2B 模型反复跑真实任务，把系统的边界撞出来 | 让本地模型"自己改项目"——它连 Rust 都写不利索 |
| 谁来修 | 主 Agent 读证据、定位、改代码、写回归 | 靠"调大超时/加重试"把指标刷上去 |
| 谁判输赢 | 固定尺子（同一批任务、同一套判分）前后测量 | 换题、换尺、换口径之后再说"变好了" |

一句话概括：**进化的是项目，不是模型。** 模型在这里相当于一个"不知疲倦但能力很弱的测试员"，它的价值不在产出，而在**稳定地把系统的薄弱处暴露成可计数的失败**。

---

## 2. 闭环怎么转：五段式

```
   ① 观测          ② 分桶            ③ 假设            ④ 修复           ⑤ 判定
真实长跑 N 轮 → 失败归因成桶 → 挑最大桶问"为什么" → 改代码 → 证据留存 → 同尺重测 → 代际比较
     ↑                                                                              │
     └────────────────────────── 不过就继续下一圈 ←────────────────────────────────┘
```

每一段都有对应的硬要求，缺一段闭环就断：

1. **观测**：必须是真起进程、真打 HTTP、真落 jsonl。判断"这轮算不算完成"不能靠肉眼，要有可在事后复核的字段。
2. **分桶**：失败必须归到**不同根因**的桶里。`status=failed` 这种粒度等于没归因——`timeout-no-output`、`no-code-at-all`、`syntax-error`、`unverified` 各自指向完全不同的修法。
3. **假设**：只挑**最大且最可疑**的那个桶动手。同时改三处，之后涨了也不知道是谁的功劳。
4. **修复**：改动要能被单独回滚，且必须写清"为什么这么改"（注释里写下踩过的坑，比写"优化"有用一百倍）。
5. **判定**：换一把新尺子量出来的结果**不能**和旧尺子的数据混在一张表里比。要么同尺重测，要么把旧数据按新逻辑重放（这就是 §5.3 要的证据留存）。

## 3. 度量三件套：谁负责什么

三件工具职责不重叠，缺一件就有一类问题看不见。

| 工具 | 位置 | 只干一件事 | 缺了会怎样 |
| --- | --- | --- | --- |
| `soak_project.py` | `scripts/` | **产生**数据：起服务、发任务、抽代码、判语法、落 jsonl | 没有真实样本，一切讨论都是猜 |
| `soak_campaign.py` | `scripts/` | **汇总**数据：多批次合并、按语言/项目/阶段/代次分层 | 只能看单批，看不出"第 N 代是否更好" |
| `evolve.py` | `scripts/` | **判定**数据：失败分桶、Wilson 区间、代际判据、判分重放 | 会把噪声当进步，把退步当运气 |

三者的关系是：`soak_project` 产粮食，`soak_campaign` 记账，`evolve` 做裁判。裁判不能自己种粮，否则一定偏心。

## 4. 凭什么说"变好了"：Wilson 区间，不是点估计

### 4.1 一个真实的反例

早前跑过一批 100 轮：达交付 62%。更早一批 148 轮去重后：45.9%。
看上去是"大幅提升 16 个百分点"，很容易顺手写进报告庆祝一下。

但样本只有几十上百，这两个数的 95% 置信区间是重叠的。`evolve.py` 遇到这种情形只会输出 **"未见显著差异"**，不给"改善"两个字。这不是保守，是**诚实**：在 100 样本量上，62% 与 45% 完全可能来自同一个真实水平。

### 4.2 判定规则（写进代码，不靠自觉）

`judge_gen()` 三层，任一不过就不算进化：

1. **样本层**：本代 ≥ 100 轮且覆盖 ≥ 2 个项目，否则直接拒绝参与比较（输出"样本不足"，不是"通过"）。
2. **质量层**：达交付率、编译通过率、完成率三项，比较 **置信区间**；出现"退化"即否决。
3. **成本层**：单位交付 token 上涨超过 20% 判为退化——靠烧更多 token、堆更多重试换来的交付率，是假进化。

结论只有四种：`通过` / `未通过（有指标退化）` / `待定（无显著变化）` / `首代（无基线）`。
**"待定"是常态**，它的意思是"还没攒够证据"，不是"没做好"。

## 5. 第一代：真修了什么（有数为证）

第一代动手前，池子里有 145 轮真实样本（去重后），状态如下：

| 指标 | 数值 |
| --- | --- |
| 样本 | 145 轮 |
| 任务完成 | 140（96.6%） |
| 达交付标准 | 82（56.6%） |
| 编译通过 | 84 / 145（旧口径，含假红，见 5.2） |

失败归因大体如下（`evolve.py --buckets` 真实输出）：

| 原因 | 轮数 | 占比 | 语言分布 | 下一刀该切哪 |
| --- | --- | --- | --- | --- |
| `syntax-error` | 36 | 24.8% | python 28 / rust 8 | 代码抽出来了但不合法，查抽取是否截断 |
| `no-code-at-all` | 19 | 13.1% | none 16 / rust 3 | 一句没写，区分提示词还是能力 |
| `timeout-no-output` | 5 | 3.4% | none 5 | 查超时与后端吞吐 |
| `not-delivered` | 3 | 2.1% | python 3 | 查判定阈值 |

第一代挑了三处动手，按"危害排序"而不是"好改排序"。

> **补记（同日晚，两次追加）**：修完前三处立刻用 `--rejudge` 重放，翻出 48 条翻案、35 条假绿（详见 5.4），
> 于是补了三处（5.4–5.6）。接着又发现"能编译但与任务无关"的玩具代码同样在骗指标（5.7），
> 再补两处（5.7–5.8）。**"第一代"最终是八处，不是三处——多出来的五处，全都是前面修完复算后才暴露的。**
>
> 这条链子本身就是结论：**假绿是分层的**。修掉第一层（`'...'`）才看得见第二层（空串），
> 修掉第二层才看得见第三层（玩具代码），修掉第三层才看得见真问题（86% 的失败根本不归框架管，见 5.8）。
> 若不修，第一层就会一直盖着下面所有层。
>
> 上表中的 `syntax-error 36 条 / 24.8%` 是**旧尺的判决**；新尺下该桶只剩 17 条（其中 rust 13），
> 真正的第一大桶是 `placeholder-instead-of-code` 92 条。这张表保留原样，作为"旧尺曾经误导我们"的存证。

> **补记（第三次追加，2026-11-16）**：`--rejudge` 又翻出 **102 条翻案**，全部指向同一件事——
> `...` 是 Python 的合法表达式，`compile("...")` 会成功，于是"只回了三个点"被记成"编译通过"（详见 5.9）。
> 同时补上 5.10：给"感知到失败"配第一个动作（分解重试）。
>
> 至此**第一代是九处尺子修正 + 一处机制改动**。这个比例本身就是结论：
> **十处里有九处在修"怎么量"，只有一处在修"怎么动"。**
> 一个系统要花九次修正才敢动一下，不算高效，但它是诚实的顺序——
> 在尺子会撒谎的时候动得越多，走错得越远。

### 5.1 修一：任务流从头就撞墙（危害：整批数据作废）

**现象**：两次启动长跑（1000 轮 / 600 轮），第 1 轮就是 `st=None agents=0 code=- 600s`，jsonl 只有几行。

**定位**：`build_goals` 按 `PROJECTS` 原序轮转，而 P1–P6 **全是 Rust**。2B 模型在 Rust 上必然吃满 `--task-timeout 600s`，于是长跑开局即卡死——前面几百轮全白烧，还占着 CPU。

**修复**：`build_goals(..., order="easy-first")`，按语言把模型更可能完成的 Python 侧项目排到前面；`--order legacy` 保留原序用于对齐历史批次。

**验证**：`build_goals(6)` → `P5/P5/P5/P6/P6/P6`；`--order legacy` → `P1/P1/P1/P1`。

**为什么这么修而不是"把超时调大"**：调大超时是掩盖。真实情况是"Rust 任务在当前模型下不可完成"，这一类必须作为**能力上限**被单独度量（所以 `--suite rs` 单列），不能混进主线把完成率拉到地板上。

### 5.2 修二：判分器把"没证据"当成"有结论"（危害：指标被系统性污染）

**现象**：47 条编译失败里，34 条的 `compile_detail` 是同一句——"worker 自检（output 被平台截断，本机无法复验）"。

**根因**：判分代码写的是 `ok = bool(mark_deliv)`。`mark_deliv` 是 worker **自报"已交付"**，语义与"代码能编译"完全不同。两个字段一混，编译列就变成一锅粥，而且方向还会随 worker 自报乱翻——一会儿假红、一会儿假绿。

**修复**：编译判定改**三态**：
- `True` 本机实测通过；
- `False` 本机实测失败；
- `None` 无法验证（无完整代码 / 缺 rustc），**不进入编译率分母**。

同时把 worker 自报值单列成 `worker_claim_delivered`，只作对照，不参与编译结论。失败归因也新增 `unverified` 桶。

**为什么必须三态**：二态的表达力不够时，人会本能地把"不知道"塞进"否"里。这在报表上看起来只是数字低了一点，实际后果是**修错方向**——你会去查模型的代码质量，而真凶是观测链路。

### 5.3 修三：判分自身不可复现（危害：改判分就要重跑几小时）

**现象**：想"拿旧数据按新判分逻辑重算"，发现做不到——落盘时每个 step 只留了 `out[:160]`（给人看的摘要），判分时用的 `out_full` 根本没存。

**根因**：只想着"证据够复盘"，没想着"证据要够重算"。这两件事的粒度差一个数量级。

**修复**：新增 `judge_evidence`，随每条样本落盘：

| 字段 | 作用 |
| --- | --- |
| `code_full` | 被判分的代码本体（超 4000 字符保留头尾并标 `code_truncated`） |
| `code_sha1` / `joined_sha1` | 事后核验"这段证据有没有被改过" |
| `marked` | 当轮用的标记值（delivered / lang / chars） |

配套 `evolve.py --rejudge`：用留存证据按**当前**逻辑重算编译结论，输出"哪些样本结论变了、往哪个方向变"。老批次没留证据的会明确报"不可重放"，**绝不猜**。

**这一条的意义**：它把"改判分器"从"几小时重跑"降级为"分钟级重算"。判分器也是代码，也会写错；不给它留重放通道，就等于把判分器钉死成不可修。

### 5.4 修四：抽取器把"没写代码"当成"代码编译通过"（危害：35 条假绿，指标被抬高）

**现象**：`--rejudge` 重放 233 条有证据的样本，48 条翻案。其中 **35 条从 `True` 翻成 `None`**，抽出来的"代码"原文是：

```
...
```

三个点。而 Python 里 `...` 是合法的 **Ellipsis 表达式**，`compile("...")` 返回成功。于是"模型啥也没写"被判成"代码编译通过"。另 13 条是 `<code here>` / `<你的代码>`，被判成语法错。

**根因**：判分逻辑只看"编译是否成功"，却没问"**喂给编译器的东西是不是代码**"。锚点上系的是抽取器的输出，抽取器抽错了，锚点就是假的——但它仍然会给出自信的成功。

**修复**（三道闸，缺一不可）：

| 闸 | 做法 |
| --- | --- |
| 结构探测 | `_STRUCT_RE` 从裸 `[=;]` 收紧为 `\w\s*\(|=`，避免 `print("hello")` 这类合法短代码被误判 |
| 占位符识别 | 命中 `<code here>`、`<你的代码>`、`(your full code here)`、裸 `...`、`TODO`、空串 → `compiles = None` + `compile_source = "placeholder"` |
| 语言猜错 | 围栏语言与内容不符 → `compiles = None` + `compile_source = "lang-guessed"`，不让它冒充编译失败 |

配套：`--selftest` 增第 4b 节，**正负样本都要有**——正样本 6 条、负样本 5 条。只测正样本时，`return True` 也能全绿。

**这一条的意义**：假红会让数字难看，人不爽，于是去查；**假绿会让数字好看，人满意，于是什么都不会发生**。35 条假绿静悄悄躺了很多轮，一直在替"编译通过率"抬轿子。

同时它也证明：**假红与假绿同源**。两者根因都不是编译逻辑，而是"抽取错了东西"。修一个判据，两个方向同时收敛——`syntax-error` 桶从 56 条降到 11 条，`placeholder` 桶从 0 变成 48 条。

### 5.5 修五：编译率的分母混进了"永远不可能通过"的轮（危害：指标系统性偏低）

**现象**：报表打"275/410"，但 410 里有 86 轮压根没产出代码（`no-code-at-all` 等），它们永远不可能算通过，却被算进了分母。

**根因**：`metrics()` 里 `compiles_pct` 的分母用的是 `judged`（非 `None` 的条数，正确），但 `show_buckets` 打印时手滑传了 `m["n"]`（总样本数）。代码对，打印错——**这种错最难发现，因为逻辑层测试是全绿的**。

**修复**：

1. `metrics()` 增 `judged`、`compiles_verifiable`、`judged_verifiable`、`compiles_verifiable_pct`、`compiles_verifiable_ci`；
2. `show_buckets` 打两行——主行分母只含可判定轮，次行为**可复验子集**（证据在手、能被当前尺子复算）；
3. `judge_gen` 的跨代比较改用 `compiles_verifiable_ci`；
4. `_cmp_rate` 加 `alias` 回落：旧基线没有新键时回落旧键并在指标名后缀「（基线口径=…）」，两边都缺则判 `不可比`——**不许因为缺键把判据链打断**。

**这一条的意义**：指标的分母就是它的诚实度。分母里混进"注定失败"的样本，等于让系统永远看起来比实际差一点；混进"无法验证"的样本，等于让假绿永远有地方躲。

### 5.6 修六：改了尺子，历史结论必须自动跟着改

**现象**：`load_samples` 读历史样本时直接用落盘的 `compiles` 字段——那是**当年那把尺子**的结论。修了四次判据，报表却还在用第一把尺子的判决。

**修复**：`load_samples` 末尾统一 `return apply_current_judge(rows)`。对有完整证据的样本，按**当前**逻辑重算，同时：

- `compiles_original` 保留旧值（可追溯"翻案前是什么样"）；
- `compile_source` 记 `local-recalc`；
- 清空旧 `failure_reason`，交给 `reason_of` 按新口径重推。

无证据的老批次原样保留，并在桶里明确标 `legacy-unverified`（33 条），**不参与决策，也不假装参与**。

配套修 `rejudge` 的对照基准：`old` 必须从 `compiles_original` 取，否则 `load_samples` 已重算过，新旧值恒等，重放结论永远是"0 条变化"——**一个永远返回"没问题"的检查器，比没有检查器更糟**。

**这一条的意义**：尺子改了，历史必须重判，否则每一代都在用不同的尺子量，代际比较全是假的。而"能重判"的前提，正是 5.3 那条证据留存。

### 5.7 修七：玩具代码骗过了编译率（危害：第三类假绿，且最会骗人）

**现象**：修完 5.4 的 `'...'` 之后，还有 26 条"明确没有交付"的样本被判成编译通过。逐条看原文，两类：

- 空串 `len=0`——`compile("")` 通过；
- `print('Hello World')`、`import os`、`import os\n# ...`——**语法完全合法，只是与任务毫无关系**。

最刺眼的一条细节：那串 `print('Hello World')` 在 camp-b、camp-e、camp-f **五个不同轮次**里反复出现，**长度完全相同（209 字符）**。同一份模板被反复背出来。

**原因**：编译通过率只问"这段字符是不是合法语法"，从不问"这是不是任务要的东西"。而 `is_placeholder` 判据刻意对 `import os` 放行——**这是对的**，因为 9 个字符确实可能是真代码被截断的开头，抽取层没有上下文。

**修复**：不动抽取层，在指标层加一维。样本里其实一直有个几乎完美的信号没人用——`delivered_code`，worker 自报交没交付：

| delivered_code | n | 代码长度 P50 | 编译通过 |
| --- | --- | --- | --- |
| True | 311 | **1352** | 310 True / 1 False |
| False | 132 | **7** | 14 False / **21 True** |
| None | 16 | 0 | 16 None |

`True` 组 311 条里 310 条可编译、P50 长度 1352、短于 120 字符的仅 1 条；`False` 组 P50 长度只有 7 个字符。**两组几乎完全可分**——那 21 条"能编译"的，全落在 `False` 组里。

于是新增主尺 **可用交付（usable）= worker 认领 `delivered_code=True` 且本机语法通过**，并新增 `stub-pass` 桶单独立账（能编译但没人认领）。

改完第一次跑出的真实数字：

| 口径 | 数值 |
| --- | --- |
| 编译通过率（可复验） | 95.7% |
| **可用交付率（可复验）** | **89.4%** |
| 落差 | **6.3 个百分点** |

那 6.3 个点，就是"能编译但没人认领"的虚高部分。

**这一条的意义**：假绿有两副面孔。`'...'` 那类是"根本没内容"，一眼可疑；`print('Hello World')` 这类是"内容合法但与任务无关"，**看起来非常健康**，光靠语法尺子永远抓不到。判分器能问的最弱的一个问题，就是"这玩意儿能跑吗"。

### 5.8 修八：加了归责——这批失败该记在谁头上

这一条不是修 bug，是修**方向**。

**现象**：分桶表按桶的大小排序，`placeholder-instead-of-code` 92 条稳居第一。按这个排序，下一刀该去改提示词。但改之前先问了一句：**这 92 条，是框架的问题吗？**

于是把 189 条失败与 413 条成功逐项对照框架行为：

| 组 | n | steps | agents | 交接 | tokens P50 | elapsed P50 |
| --- | --- | --- | --- | --- | --- | --- |
| 成功 | 413 | 全是 4 | 全是 3 | 1239（3.0/轮） | 937 | 112s |
| 交不出东西 | 189 | 全是 4 | 全是 3 | 537（2.84/轮） | 607 | 185s |

**两组框架行为完全一致**。步骤数相同、agent 数相同、交接率几乎相同。差别只有两处：失败组吐的字少 35%，花的时间多 65%。

再看一条具体样本：`P10 任务队列 r215`——`status=succeeded`、`steps=4`、`agents=[super-agent, code-agent, guard-agent]`、`handoff=3`、`tokens=604`、`elapsed=219.63`、**`code_chars=3`**。流程整整跑满四步、三个 agent 都到场、交接三次，最后交出来的是 `...`。

而它自己的 payload 里明写着 `delivered_code: false`、`summary: ""`——**worker 一开始就知道自己没交付。**

**归责判据**（`blame_of`）：

| 归责 | 判据 | 轮数 |
| --- | --- | --- |
| framework | steps/agents 为 0（流程没起来），或输出取不全 | **23** |
| model | 流程跑满四步仍写不出东西 | **162** |
| unknown | 旧口径残留、证据不在 | 33 |

**162 : 23。** 也就是说，这批失败里只有 **12%** 是框架能修的：10 条 `timeout-no-output`（steps=0，600s 内一步没走，多半是并发争抢 CPU）+ 13 条 `unverified`（tokens P50=1255，全样本最高，却取不全代码，是输出通道截断）。

剩下 86% 是模型能力边界。`placeholder` 92 条、`stub-pass` 24 条、`no-code-at-all` 25 条、`syntax-error` 17 条——**全是 model，改了框架也不会动一个数**。

**这一条的意义**：这是整套闭环里最容易跳过、也最贵的一步。没有归责，"下一个靶心"只能按桶的大小选，而**桶的大小和"框架能不能修"完全是两件事**。拿着 92 条 placeholder 去改提示词，改完数字纹丝不动，还会误以为"改得不够狠"，接着改第二轮、第三轮——这就是最典型的假进化：很忙，很累，没进步。

还有一个更值得记的发现：**框架已经感知到了失败（`delivered_code=false`），却没有据此改变策略**。它只会一直试到超时，或者退化成背 hello world，然后把"我没交"如实写进 payload，仅此而已。感知到了，但没有行动——**这才是自进化真正的缺口**，而且它在框架这一侧，可以修。

### 5.9 修九：占位符是合法语法，所以它是最安静的失败（危害：21% 的轮次在污染分母）

这一处是 `--rejudge` 翻出来的，不是看报表看出来的。

拿留存的证据按新逻辑重放，**481 条可重放样本里 102 条结论变了**：71 条 `True→None`、31 条 `False→None`。一条都没改向（没有 `True→False`，也没有 `False→True`），全部是"从有结论"变成"踢出分母"。

理由全部一样：**占位符**。

被翻掉的这 102 条，代码长度中位 **3 个字符**，82 条不超过 10 个字符。3 个字符是什么？是 `...`。

而 `...` 在 Python 里是 **Ellipsis 字面量**，是一个完全合法的表达式。`compile("...", "<s>", "exec")` 返回成功。

于是出现了这个项目里最安静的一种假绿：

> 模型一行字都没写，只回了三个点，编译器说"没问题"，判分器记下"编译通过"。

它比空串更隐蔽（空串很可疑，`...` 很像"我写完了但省略了"），比 hello world 更隐蔽（hello world 至少是主动背了个模板），**也比两者都更常见**：camp-e 239 条里 53 条、camp-f 246 条里 49 条，约 **21%**。

修完之后有个很反直觉的数：

| 口径 | 编译通过 | 说明 |
| --- | --- | --- |
| 旧口径（占位符算结论） | 437/485 = 90.1% | 分母里混着空壳 |
| 新口径（占位符不算结论） | 366/383 = **95.6%** | 分母只剩真写了字的 |

**踢掉 102 条垃圾，通过率反而涨了 5.5 个百分点。**

这一点值得停一下。通常"清掉脏数据"会让人以为数字要变难看，这里反过来了——因为占位符里有 31 条原本被判成"编译失败"（`TODO`、`<code here>` 之类送去编译器必然报错），71 条被判成"编译通过"（`...`）。两类垃圾一起把分母撑大、把比例拉低。真实情况是：**凡是真动手写了的轮次，95.6% 都能编译通过。**

所以"21% 的轮次只交了三个点"这件事，从来不是编译率能反映的问题。编译率回答的是"写出来的东西对不对"，而这 21% 是"根本没写"。

**两个数字混在一个分母里，两个都会失真**：编译率被拉低（显得模型写不对），交付率被拉高（显得模型交了东西）。这就是为什么必须分两个尺子量、并且各自剔除对方的分母。

金句留在这一节：**最安静的失败，是那种语法完全正确的失败。**

### 5.10 修十：给"感知到了失败"配一个动作——分解重试（本代的第一次真正行动）

5.8 最后留了一句不太好听的话：框架已经感知到 `delivered_code=false`，却什么也没做。

这一处就是补那个动作。它跟前面九处的性质不同——**前面九处都在把尺子改准，这一处是第一次让尺子去改变行为**。

设计上只做了三个决定，每个都有实测依据：

**一、判据用两个条件，不用一个。**
"可用交付" = worker 认领交付 **且** 本机实测能编译。只用"能编译"会被玩具代码骗（5.7）；只用"认领交付"会被 worker 的自述骗（5.2，34 条自报"output 被截断，本机无法复验"）。两个条件同时成立才算数。

**二、只做两轮，不做三轮。**
两轮已经把单轮成本翻倍。第三轮的边际收益必须先由数据证明，否则就是在尺子还没校准的时候引入第三个变量，把一次干净对照做废。

**三、按"上一轮留下了什么"分两种打法。**

| 上轮状态 | 打法 | 为什么 |
| --- | --- | --- |
| 有骨架（≥120 字符） | **接力补全**：把上轮代码原样塞回 prompt，要求在既有结构上补完 | 从零重写时最常见的退化就是背模板（同一份 209 字符 hello world 在五个不同轮次出现）；骨架进了 prompt 至少把话题锚死 |
| 无骨架 | **降粒度**：只要一个核心函数，砍掉 main、参数解析、测试 | 2B 在 CPU 上整包交付几乎必败，但"写一个函数"是它能过的量级 |

第三条正好打 5.9 那个靶：**21% 的轮次交纯占位符，不像"不会写"，更像"一次要得太多就只给省略号"**。如果是后者，降粒度就该有救回率；如果是前者，救回率会是零。这个实验能把两件事分开。

工程上做了三条克制：

1. **三本账分开**：主样本（首轮）、`-retry`（第二轮）、`-decomp`（结论行）。开一个实验开关，不该让任何历史口径变一个字。
2. **`load_samples` 里立刻拦掉派生文件**。这是个差点踩进去的坑：`-retry` / `-decomp` 都命中 `*.jsonl`，而它们的 tag 与主批次不同（`camp-g-retry` ≠ `camp-g`），所以 `(tag, round)` 去重**拦不住**——放进来就是样本量虚增、成功率虚高。新加一列数据，先想清楚它是"证据"还是"又一个样本"。
3. **排除 `timeout-no-output`**：那是 steps=0，框架侧没跑起来，分解只会再多等 600 秒白烧 CPU。这批归 framework，要用超时阈值治，不该混进"模型多轮能不能写出来"的实验里。

`selftest` 从 21 项扩到 34 项，正负样本都测（`usable_of` 四种组合、两条打法、三种结论）。**只测"该重试的都重试了"，一个永远返回 False 的函数也能全绿**——这条教训已经吃过一次了。

验证方式：`camp-g`（带 `--decompose`）对 `camp-h`（不带），同轮数同任务流，看 `evolve.py --decomp` 报出来的救回率。在拿到这个数之前，这一处只能算"接上了"，不能算"有效"。

## 6. 反假进化条款（防自己骗自己）

这几条是硬约束，写在 `evolve.py` 里而不是写在文档里，因为写在文档里的规则最容易被"这一次特殊"绕过去。

1. **不许换尺**：改判分逻辑后，必须 `--rejudge` 重放旧数据，或整批重测；新旧口径禁止混在一张表里比较。
2. **不许合并口径**：`unverified`、`timeout`、`syntax-error` 三类失败不能合成一个"失败率"再吹嘘下降。
3. **不许只看均值**：交付率必须带置信区间；耗时必须给 P50 + P95（P95 才是用户真正会撞见的那一次）。
4. **不许单点样本**：样本 < 100 轮或只覆盖 1 个项目的代次，只能记档，不能进判定。
5. **不许成本失控**：单位交付 token 上涨 > 20% 直接判退化，哪怕交付率涨了。
6. **不许把"待定"说成"成功"**：无显著变化就是无显著变化。

## 10. 这份文档的立场

工程上最容易发生的不是"做不出来"，而是"做出来了但自己不知道做得好不好"。上面十个修复里，只有一处（5.1）是真正的功能缺陷——它会让整批数据作废。其余八处（5.2–5.9）都不改变程序行为，只改变**判断是否失真**。而失真比崩溃更难发现，因为它一直"看起来正常"。

更值得记住的是它们的**暴露顺序**：前三处是"看数据看出来的"，中间五处是"重放复算翻出来的"。如果不做 5.3 的证据留存，5.4 那 35 条假绿永远不会现身，5.9 那 102 条翻案也无从生起——**你不会发现一个你没有能力复查的错误**。

假绿的层级也越挖越深，而且每一层都比上一层更会装：

| 层 | 形态 | 为什么能骗过编译器 |
| --- | --- | --- |
| 一 | `'...'` 带引号 | 被当成字符串，不是代码 |
| 二 | 空串 | 空文件也是合法模块 |
| 三 | 玩具代码 | 语法对、能跑、但和任务无关 |
| 四 | `...` 省略号 | **它是 Ellipsis 字面量，语法完全合法** |

第四层是最安静的：它不像"写错了"，它像"我写完了但按惯例省略"。而它占 21%。

而第八处（归责）和前面七处不是一个种类：前七处让尺子变准，第八处让尺子**知道自己在量谁**。它给出的结论是全篇最不舒服的一条——**86% 的失败不是这个系统的问题**。承认这一点，等于承认前七处修完，指标也不会好多少；但不承认，就会把接下来几个月花在改一个改不动的地方。**但承认之后还是要动手**，这就是第十处：既然 86% 归模型，那就不能在框架侧改提示词，只能在框架侧改**给模型的任务形状**——降粒度、接力补全，都属于"框架改变模型面对的问题"，不属于"逼模型变强"。这是框架唯一有权限做的那件事。

十处里九处修尺子、一处改动作，比例难看，但顺序诚实：**在尺子会撒谎的时候动得越多，走错得越远。**

自进化循环真正的产出，不是某一版更好的代码，而是**一把握得住、能量得准、并且知道该量谁的尺子**。尺子稳了，后面每一条设计方向（见 `89-agent-design-trends.md`）才有讨论的基础。
