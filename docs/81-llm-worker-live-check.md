# 81 · worker 接入本地模型实测记录（MiniCPM 2B / Ollama）

> 结论先说：**通了，是真的在算，不是规则假装。** `doc-agent` 已接入 Ollama 上的面壁智能 2B 模型，端到端两次复现全绿，单步耗时 100 秒量级（CPU 推理）。同时踩到 5 个坑，其中 3 个属于接口契约不一致，建议排期修。

- 日期：2026-11-11
- 模型：`minicpm5-2b:f16`（3.5 GB，Ollama 本地）
- 后端：`super-agents.exe`（`target-gnu/debug`，GNU 工具链）
- 探针：`scripts/probe_llm_live.py`（本轮新增，可一键复跑）

## 1. 接线方式（就这四个变量）

后端把配置注入给 worker 的环境变量：

| 变量 | 本次取值 | 作用 |
|---|---|---|
| `SA_LLM_BASE` | `http://127.0.0.1:11434/v1` | OpenAI 兼容地址（Ollama 自带 `/v1`） |
| `SA_LLM_MODEL` | `minicpm5-2b:f16` | 模型名，必须与 `ollama list` 完全一致 |
| `SA_LLM_KEY` | `ollama` | 本地模型随便填，但变量得在 |
| `SA_LLM_TIMEOUT` | `300` | worker 等模型的秒数 |
| `SA_RUNNER_TIMEOUT_DOC_AGENT` | `300` | **该 agent 的单步超时**，默认 20s 必被砍 |

> 关键点：`SA_RUNNER_TIMEOUT_*` 是**运行治理层**的超时（进程级强杀），`SA_LLM_TIMEOUT` 是**worker 内部**等模型的超时。两个都要放开，只放一个照样失败。

## 3. 模型产出质量（客观记录，不美化）

`doc-agent` 实际输出（第二次）：

> 文档骨架已生成（模型 minicpm5-2b:f16）：4 个小节，主题「一份把 worker 接入本地小模型的试点报告，」，耗时 102.5s。

骨架共 4 节：`试点背景与模型接入` / `接线方式与配置` / `实测数据采集` / `数据分析与结论`，每节 2 条要点。评价：

- ✅ 结构完整，章节顺序合理，"实测数据采集"这类要点也算贴题；
- ⚠️ 内容偏笼统，属于"能用的骨架"，还不能当正式报告；
- ⚠️ 主题尾部带一个孤立的 `，`——取自 goal 的截断，**建议 doc-agent 对标题做去尾标点 + trim**；
- ⚠️ `keywords` 被切得很碎（`worker` / `入本地小` / `写一份把`），这是上游规则实现的定长切词，不是模型的问题，但会污染提示词，建议改为按标点/空格切分。

模型自报的记账（可信度参考）：`reasoning_chars=2090`、`completion_tokens=1122`、`attempts=1`、`elapsed_ms=111809`。也就是说它确实先推理了 2000 多字再产出结构，**不是直接吐模板** —— 这 100 秒花在推理上，符合预期。

对 2B 量级来说，"能出结构正确的骨架"已经是合理水位。要写正式文档，建议后面接 7B 以上，或走"小模型出骨架 + 大模型填内容"的两段式。

## 4. 性能真相：模型跑在 CPU 上

`ollama ps` 显示该次加载 `size_vram = 0`、`size = 3.5 GB`、处理器为 100% CPU。也就是说这 100 秒是纯 CPU 推理的结果。

> 如果这台机器有可用的显卡，把 Ollama 的 GPU 支持打开（检查驱动 / `OLLAMA_*` 相关设置），同一模型的速度通常能上一个量级。这一步**没做**，需要老板定：先确认显卡是否愿意给 Ollama 用。

另外一个观察：模型常驻内存时第二次调用会快一些（111.9 → 102.6），保持常驻（`expires_at` 策略）对交互体验有意义。

## 5. 踩到的 5 个坑

| # | 坑 | 现象 | 处理 |
|---|---|---|---|
| 1 | 超时覆盖键写成 `SA_RUNNER_TIMEOUT_DOC-AGENT` | **不报错、不生效**：每步 20s 被强杀 → 重试 3 次 → 任务 `partially_succeeded` | 正确键为 `SA_RUNNER_TIMEOUT_DOC_AGENT`（大写 + `-` 换 `_`）。已在文档与脚本注释中固化 |
| 2 | `GET /tasks/{id}` 实际返回**平铺结构** | 与 `openapi.json` 的 `TaskDetail{task, trace, memory_refs}` 不一致；按契约写会拿到 `undefined`，探针因此空转 | 暂时在客户端做兼容；**建议修契约或修实现，让二者一致** |
| 3 | 注册要 `username`，登录要 `account` | 同一套账号，两端字段名不同，照着一个抄必错 | 客户端各写各的；建议统一 |
| 4 | `POST /tasks` 同步执行 | 请求挂 100s+，客户端 30s 超时会误判失败（任务其实在跑） | 探针把超时给到 600s；**建议改 202 + SSE 推进度** |
| 5 | `trace.at` 是"完成时刻"不是"开始时刻" | `sandbox/started` 与紧随其后的 `execute` 相差 30 微秒，按"开始→结束"配对会算出 0 秒 | 一律用"相邻完成点做差"；详见 `80-replay-timeline.md` §3 |

坑 1 值得单独说：它**静默失败**——不报错、不警告，只是每次都超时。如果没有"拿真实时长交叉验证"这一步，很容易被误判成"模型太慢"。

## 6. 怎么复跑

```bat
:: 1. 确认模型在
ollama list

:: 2. 确认 Ollama 在跑
curl http://127.0.0.1:11434/v1/models

:: 3. 复跑探针（二进制不在项目内时用 --exe 指定）
python scripts\probe_llm_live.py --model minicpm5-2b:f16 ^
    --exe "C:\Users\<user>\Desktop\build_sa1\target-gnu\debug\super-agents.exe"
```

脚本会自己：起后端（注入上表变量）→ 注册临时账号 → 提交任务 → 拉详情 → **打印时间轴** → 跑 P1/P2/P3 三条断言 → 落 `evidence.json`。

退出码：`0` 全绿 / `1` 未全绿 / `2` 环境不通（会指出卡在哪一步）。

断言含义：

- **P1** worker 输出里出现模型名 → 证明 `SA_LLM_*` 真的透传进了子进程
- **P2** 该步 tokens > 0 → 证明不是走的规则降级路径
- **P3** 路由命中预期 agent 且成功 → 证明接线对，不是别的 agent 顶包

## 7. 遗留待办（按优先级）

1. **契约对齐**（坑 2、3）：`openapi.json` 与真实响应不一致，属"门禁没抓到"的漏洞。建议补一条"响应 JSON 形状 vs schema"的契约测试。
2. **`POST /tasks` 改异步**（坑 4）：`202 + task_id`，进度全靠 SSE。这条同时是前端时间轴的前提。
3. **GPU 加速**（§4）：需要老板确认是否把显卡给 Ollama。
4. **doc-agent 小瑕疵**：标题去尾标点、关键词切分规则。
5. **多模型对比**：同一 goal 跑 2B / 7B，把耗时与质量做成一张表，用于决定日常用哪个。
