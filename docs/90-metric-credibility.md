# 90 · 指标可信度声明（metric credibility）

> 这份文档不描述能力，只回答一个问题：**报表上那些数字，哪些能拿去做决策，哪些不能。**
>
> 写它的直接原因：本项目历史上出现过两次"全绿但没证明到"——门禁全过报表却整体失真。
> 所以凡是要拿去汇报、拿去判断"模型行不行"的数字，必须先说清它是在哪把尺子下量的。

---

## 一、一句话结论

**体系不是瓶颈，模型能力是瓶颈——这个结论成立，但它只对 119 条（camp-g）严格成立；
更早的 605 条历史样本需要按修正后的读数看，其中 73 条属于"旧报表算过、实际是空的"。**

修正方向**恒为往下**（旧报表高估），没有出现"旧判太严冤枉了模型"的情况（误杀纠正 = 0）。
这一点本身就值得记住：**判分器的错误几乎总是往"让结果好看"的方向错**，不会反过来。

---

## 二、分水岭：两把尺子

| 批次 | 条数 | 尺子 | 读数可信度 |
| --- | --- | --- | --- |
| camp-g | 119 | **新尺子**（防伪判据 + 占位符单列 + `--crate-type lib`） | 可直接引用 |
| camp-a / b / e / f 及其它历史批次 | 605（可重放） | 旧尺子 | 必须先看第四节的重放修正 |

新尺子做了四件事，每一件都对应一个真实踩过的坑：

1. **`...` 不再算实现**。`...` 是合法的 Python 表达式，`py_compile` 直接给过。
   261 轮重放里 217 条 compiles=True，剔除后只剩 179——**虚高 17.5 个百分点**，
   而剔除的 38 条里有 37 条正文就是三个点。
2. **子进程解码改成 `utf-8 + errors="replace"`**。原来按 GBK 读子进程 stdout，
   撞到非 GBK 字节就抛 `UnicodeDecodeError`，线程崩溃把真错误盖住，
   表现为"编译失败了但不知道为什么"。
3. **Rust 检查补上 `--crate-type lib`**。漏参时合法库代码（无 `main`）会被 E0601 判死，
   那是判分器自己造的错误，不是模型不会。
4. **`is_substantive` 五刀**：`pass` / `todo!()` / 只写函数签名 / hello-world 模板 / 空实现，
   五种"语法合法但没有实现"的交付一律不计入通过。

这四条现在由**门禁 26 `check_judge_cheat.py`** 站岗：拿 9 种假交付去骗、拿 4 种真实现去撞，
两头都必须守住。它自己也要能被证伪——`--drill` 要求同一份合法 Rust 代码
用漏参方式编译必须报 E0601、用正确方式必须通过，一红一绿并排才算有判定力。

---

## 三、camp-g 的 75.6% 是怎么来的（可信）

`docs/evidence/soak/soak-camp-g.jsonl`，119 条，全部 `status=succeeded`（主动停，不是跑崩）。

| 指标 | 数值 |
| --- | --- |
| 编译通过 | 90 / 119 = 75.6% |
| 不可用 | 29 / 119 = 24.4% |
| `compile_source=local` | 95 |
| `compile_source=worker-unverified` | 3 |
| `compile_source=placeholder` | 21 |
| compiles=True 但正文是 `...`/`pass`/空 | **0 条** |
| compiles=True 且 code_chars<20 | **0 条** |

**为什么这个 75.6% 可以信**：占位符 21 条被单独标成 `compile_source=placeholder`，
没有混进"编译通过"里数；compiles=True 的 90 条里一条三点式都没有。
换句话说，这把尺子下"通过"意味着"编译器认、且里面有东西"。

21 条占位符的项目分布：P10 任务队列 9、P9 微服务接口 6、P6 API 文档生成 4、P5/P8 各 1。
这个分布不是随机的——**占位符集中在"要同时写多个模块"的题上**，单文件小函数的题几乎不出占位符。
这直接引出冲刺二的假设：是不是该把这些整包任务拆开做。答案见 `docs/91-split-strategy.md`。

## 四、605 条历史样本的修正读数

由 `scripts/rejudge_soak.py` 用**当前**判据重跑历史存下的代码得到，原始报告在
`docs/evidence/judge-replay.md`。范围：全部批次，可重放 605 条，因代码截断存证跳过 0 条。

| 语言 | 可重放 | 误杀纠正 | 虚高剔除 | 仍失败 | 仍通过 | 旧也未判 |
| --- | --- | --- | --- | --- | --- | --- |
| py | 588 | 0 | 73 | 36 | 458 | 21 |
| rs | 17 | 0 | 0 | 17 | 0 | 0 |

六列之和 = 可重放（py：588 = 0 + 73 + 36 + 458 + 21；rs：17 = 0 + 0 + 17 + 0 + 0），这是硬校验：
**踩过的坑是表格只有四列，py 行加起来 581 而非 602，差 21 条没有列承接，读者只能自己猜。**
那 21 条是 `old=None`——旧报表当年根本没给出编译结论，它们既不算误杀也不算虚高。

**这张表本轮改过两处，两处都是量具的错，不是模型的错**（详见 §5.2）：
① `rs` 从 3 条变 17 条、`py` 从 602 条降到 588 条——历史上 14 条 Rust 样本被当成 Python 判了；
② 与之对应，`py` 的「仍失败」从 50 降到 36——不是 Python 突然变强，是 14 条错判被搬回了正确的桶。
**合计仍是 605，一条没多一条没少。** 这正是先对总数、再对分桶的价值：分桶错了，总数会立刻告诉你。

虚高剔除 73 条的构成：占位符 71 条、`hollow`（语法合法但无实质）2 条。
**早先这里写"占位符 122 条"是错的**：那个数字把"旧判本来就没通过的占位符"也算了进去，
而它们从来没被算进旧报表的通过数，谈不上"被剔除"。修正后与表三严格对齐。

## 五、必须打折看的三处

这三处不是"数字不准"，而是"数字对了但不能推得太远"。对外引用时请连结论边界一起引用。

### 5.1 Rust 的 2.0%（51 条里 2 条）

样本太少，且与 Python 不同——Rust 的失败不是"偶尔写错"，是**结构性不会**：
15 条标 `rust` 的样本 0 通过，51 条 `rs` 里占位符 9 条。
把小模型换成大模型能不能解决，**本轮没有验证**，不许当成"切分能救"或"重试能救"来引用。

### 5.2 语言标签：已经归一，但归一之前的所有按语言数字都作废

同一个语言曾经被记成两桶：`py` 630 条 90.5%、`python` 110 条 61.8%，差 29 个百分点。
那不是能力差别，是**标签来源差别**——新批次写 `code_lang="py"`，老批次写成全名 `python` / `rust`。

更糟的是它连累了一把尺子：`scripts/rejudge_soak.py` 取语言时只读 `judge_evidence.lang`，
而这个字段**从来不存在**（语言在顶层 `code_lang`），于是每一行都落到 `or "py"` 的兜底——
**全部 Rust 样本被送进 `py_compile`，必然语法错**，然后被诚实地记成「仍然失败」。
这是本项目量具的**第四次翻车**，前三次分别是：`...` 当实现、GBK 吞子进程输出、文档数字不比对代码。
四次形态完全一样：**错的不是被测系统，是读它的那只手**；而且每次读数都很「干净」，干净到没人怀疑。

已修：`norm_lang()` 把 `python` / `py3` → `py`、`rust` → `rs`；缺字段标 `missing-lang` 而不是悄悄当 py；
表三改为遍历**实际出现**的语言，而不是写死 `("py", "rs")`——写死时漏行是静默的，
六列和校验管得了行内、管不了漏行。

**所以 2026-11-16 之前的任何「按语言」百分比一律作废重读**，包括本文早先版本里的 630 / 110 两组数。

### 5.3 三个桶在真实会话上是空的

压缩模块的"计划 / 判据 / 下一步"三桶，在**合成会话**上计数为 0——不是没实现，
是合成样本里根本没有锚点句。真实会话的端到端验证至今没做：soak 存的 jsonl 是压测统计记录，
不是 `[role, content]` 会话，喂不进 `_compact.py`。
**所以"方向保持"这件事，目前只在手工构造的样本上成立。** 这是已知的覆盖缺口，不是已证结论。

## 六、给后续使用者（含前端）的三条规则

1. **看到"编译通过率"先问哪把尺子。** 2026-11-16 之前的批次一律按第四节修正后的读数用，
   不许直接引用当时写下的百分比。
2. **"旧也未判"不是失败。** 旧报表没给结论的 21 条既不算通过也不算失败；
   把它们算进失败会低估模型，算进通过会重演虚高。
3. **看语言分布先问有没有归一。** 见到 `py` 与 `python`、`rs` 与 `rust` 并列成四行，
   先确认脚本有没有 `norm_lang()`；没归一的分桶会把同一门语言劈成两种能力。
4. **门禁全绿不等于报表可信。** 门禁 26 守的是判分器、门禁 27 守的是文档数字，
   两者都过了才叫"报表能看"。这两道门之所以存在，就是因为前 25 道全绿的时候，
   报表还在骗人。
