# 89 · Agent 设计趋势与本项目对照：从「能管住」到「会变好」

> 一句话：**趋势不是拿来追的，是拿来当镜子照的。**
> 这份文档把当下 Agent 工程的几条主线摊开，逐条对照本项目现状打分，然后只挑三件"便宜且收益大"的事动手。
> 前置文档：`88-self-evolution-loop.md`（闭环与尺子）。本篇讲方向，88 讲纪律。没有 88 的尺子，本篇全是空谈。

## 0. 趋势判断：三条主线，一条暗线

把近一年的 Agent 工程实践摊开，能落到地上的趋势集中在三处，另有一条贯穿它们的暗线。

| 主线 | 核心变化 | 一句话本质 |
| --- | --- | --- |
| **异构化** | 从"一个模型打所有活"到"按认知功能分层配模型" | 让 2B 做它擅长的（感知、试错），让大模型只在关键处出手 |
| **并行化** | 从"串行走完一步再走下一步"到"fan-out 探索、单点收敛" | 探索可以无限并行，**写入必须过一道闸门** |
| **可验证化** | 从"生成即交付"到"生成-验证-修订（G-V-R）" | 生成的答案不算答案，**被独立验过的才算** |

那条暗线是**预测**。前三条都把系统变复杂了，复杂度一上来，最稀缺的资源就从"模型能力"变成"时间与算力的预算分配"。谁能事先估出"这件事大概要花多久、值不值得做"，谁才能在同等算力下走更远。

### 一个反直觉的判断

这四条里，**可验证化是唯一能立刻见效的**，异构化是最后才该做的。理由很朴素：可验证化是把已有能力用好，异构化是买新能力。买之前先用好手头的——否则你连"新模型到底有没有帮忙"都量不出来。

## 1. 照镜子：八维对照打分

### 1.1 打分表

评分口径（5 分制，只标整数，避免"3.5 分"式的自我安慰）：

- **5** 有实现、有度量、有回归保护
- **4** 有实现、有度量，缺自动回归
- **3** 有实现，无明显度量
- **2** 部分实现或仅有设计
- **1** 基本没有

| # | 维度 | 得分 | 依据（本项目真实状况） | 缺口 |
| --- | --- | --- | --- | --- |
| 1 | **可观测性** | **5** | `soak_project` 每轮落 jsonl、`judge_evidence` 支撑事后重放、`evolve --buckets` 能把失败归到根因桶 | 无，这是最强项 |
| 2 | **治理与安全** | **4** | 26 道门禁、负向演练 8/8、端口段体检 + `pick_port_block` 自动避让 | 缺运行时策略（准入/限流/预算）动态化 |
| 3 | **工具与行动** | **4** | 多 agent 能起进程、打 HTTP、写文件、抽代码、跑编译器 | 工具返回缺结构化契约，worker 常把"我猜"当"我看到" |
| 4 | **多智能体协作** | **3** | 多 agent 命中 99.3%、交接 441 次，能跑通分工 | 交接靠自然语言，缺结构化 payload；无冲突消解 |
| 5 | **推理与规划** | **2** | 有任务分解，能拆子任务 | 无预测、无中途目标复核、超时阈值是拍脑袋定的 |
| 6 | **记忆与知识** | **2** | 有长期记忆目录（gotcha / knowledge / workflow / user.*） | 缺检索、缺去重、缺冲突消解、缺时间衰减 |
| 7 | **自适应性** | **2** | 88 号闭环已能"度量 → 修 bug" | 只覆盖代码缺陷，不含策略自适应（超时/并发/token 预算） |
| 8 | **多模态** | **1** | 基本无 | 全链路文本 |

### 1.2 结论：一句话定位

> **这是一个"能管住"的系统，还不是一个"会自己变好"的系统。**

强项集中在「看得见」和「管得住」——可观测性 5 分、治理 4 分。这两项恰恰是大多数 Agent 项目最弱的地方，值得守住。
弱项集中在「想得远」和「记得住」——规划 2 分、记忆 2 分、自适应 2 分。这三项是系统从"能干活"往"越干越省"跃迁的门槛。

但有个细节必须说清楚，否则这张表会误导人：**可观测性和治理能拿高分，不是因为设计得好，是因为它俩是唯一反复栽跟头的地方。**
附录 A 里那五层假绿、十处尺子修正，全是被坑出来的。**维度分不是设计出来的，是被失败打出来的**——所以一个维度今天弱，往往只是因为还没被它坑过，不代表它现在不致命。
换句话说：这张表读的是"病史"，不是"体检报告"。规划 2 分意味着"还没被规划失误坑到痛"，而不是"规划一定没问题"。

### 1.3 换个视角看：认知功能映射

八维是按工程切面切的，容易看不出病根。换成认知功能再看一遍，问题会清楚很多。

| 认知功能 | 对应维度 | 得分 | 判断 |
| --- | --- | --- | --- |
| 感知 | 多模态、输入解析 | 1–2 | 最弱，但对本项目不致命（任务几乎全是文本） |
| 认知 | 推理与规划 | 2 | **真正的瓶颈** |
| 行动 | 工具与行动 | 4 | 够用 |
| 记忆 | 记忆与知识 | 2 | **第二瓶颈**，且与认知耦合（记得住才规划得准） |
| 元认知 | 可观测性 + 治理 + 自适应 | 4 | **超配**，是差异化 |

这张表里最值得注意的反差是：**元认知是超配的，认知与记忆是欠配的。**

通俗说：这个系统很擅长"事后检查自己做得对不对"（26 道门禁、失败分桶、代际判定），但不太擅长"事中想清楚该怎么做"（无预测、无复核、无记忆检索）。

这个结构其实很罕见——大部分项目反过来：想得多、查得少。所以我们手上的资产不是浪费，而是一个**已经装好的显微镜，等着拿去看更细的东西**。方向不该是"再加强治理"，而是"把治理省下来的信任，花在认知与记忆上"。

## 2. 异构化：按认知功能配模型

### 2.1 现状的问题

当前是**单模型打所有活**：`minicpm5-2b:f16` 既要做任务分解，又要写 Rust，还要自检。这是最大的架构性浪费——用一个只会写短文的小模型去干编译器级别的活，结果必然是 `syntax-error` 占 24.8%。

88 号文档里的失败分桶其实已经给出了分层依据：

| 失败桶 | 指向的能力 | 该由谁干 |
| --- | --- | --- |
| `no-code-at-all`（13.1%） | 理解任务 | 感知层，小模型够 |
| `syntax-error`（24.8%） | 写出合法代码 | 认知/行动层，需要更强模型 |
| `not-delivered`（2.1%） | 遵循格式 | 感知层 |
| `timeout-no-output`（3.4%） | 吞吐 | 与模型大小强相关 |

四类失败指向**完全不同的能力层级**，用同一个模型去打，等于把四种病当一种治。

### 2.2 分层方案

| 层 | 职责 | 建议规格 | 判断理由 |
| --- | --- | --- | --- |
| **感知层** | 任务分类、格式抽取、路由、快筛 | 2B（现行模型） | 高频、低难度、失败代价低，越便宜越好 |
| **认知层** | 规划、分解、目标复核、仲裁 | 14B 级 | 调用次数少但错一次全盘歪，值得上大模型 |
| **行动层** | 写代码、改代码 | 30B 级 | 直接决定 `syntax-error` 与编译率 |
| **裁判层** | 判分、归因 | **保持确定性代码** | 绝不能用 LLM 当裁判（见 88 号 §5.2 假绿事故） |

最后一行是硬约束，不是建议。**裁判必须是确定性的。** 一旦让模型判模型，尺子就软了，前面所有度量全部作废。

### 2.3 一个必须记住的反例：DeepSeek 不做模型异构

2026-10-31 DeepSeek Harness 团队公开的《Super-agent 设计探索》里，原型 `dsh-superagent-prototype`（MIT）走的是**单模型强 + 系统层调度**：Router 与 Worker 用同一类模型，异构体现在**角色与上下文**，不在模型权重。

这说明异构化不是教条。判断条件很清晰：

- **模型足够强时**：异构的收益会被调度开销吃掉（多一次转手、多一次上下文重建），不如把调度做好；
- **算力受限时**（本机纯 CPU、单发约 5 tok/s）：异构是唯一能同时满足"成本可接受"与"关键步骤质量"的路。

我们现在处在后者。所以异构对本项目成立，但理由不是"趋势如此"，而是"这台机器的算力逼的"。一旦上到 GX10 集群（384GB 统一内存），这个结论要重新评估——**记在这里，免得将来把临时手段当信仰。**

### 2.4 怎么验证分层真有用

不能靠感觉。用现成测试台做三组对照，同一个 `--suite py`、同一批项目、同一判据：

| 组 | 配置 | 预期 | 若不符说明什么 |
| --- | --- | --- | --- |
| A（基线） | 全 2B | 达交付 ~55%、syntax-error ~25% | —— |
| B | 2B 感知 + 14B 认知 + 30B 行动 | 达交付 ↑、syntax-error ↓ | 分层无收益 → 瓶颈不在模型而在提示与校验 |
| C | 全 30B | 质量最好但成本最高 | 若 C 与 B 接近，说明感知层用小模型是对的 |

判据三项：达交付率（Wilson 区间）、**单位交付 token**、P95 耗时。只看第一项会得出"越大越好"的错误结论，因为更大的模型一定更贵，而贵必须换来值得的东西。

## 3. 并行化：探索可以散，写入必须收

### 3.1 趋势本身

主流做法是 **fan-out 探索 + 单点收敛**：多个 worker 各自从不同角度试，谁先跑通谁提交；提交动作串行化，避免互相踩。

### 3.2 我们付过的学费：D4i 端口竞态

门禁 10（D4i）曾经出现过一个极隐蔽的故障：上一轮残留的 `super-agents.exe` 占着 18198 端口，新实例启动时**没有报错**，而是打到了旧实例上。结果是——

> **假红与假绿同源。**

失败的那条其实是旧实例在报错，通过的那条其实是旧实例在应答。检测器本身被污染了，而它显示一切正常。

这个坑的通用教训是：**并行的敌人从来不是并发数，而是共享的可写资源。** 端口、文件、git 索引、Ollama 的推理队列，全都是写入点。

### 3.3 由此得到的设计原则

| 操作类型 | 可否并行 | 闸门 |
| --- | --- | --- |
| 读（读文件、查状态、探测端口） | 无限并行 | 无 |
| 算（推理、分析、试写草稿） | 受算力约束（本机约 2 路） | 无，但要算预算 |
| **写**（占端口、写文件、git 提交、改共享状态） | **必须串行** | 单一写闸：端口租约 + 文件锁 |

落到多 agent 架构上就是：**worker 并行思考，Router 串行提交。** 这恰好和 DeepSeek 的 Router/Worker 分离同构——他们是从调度效率出发，我们是从假红假绿的血坑出发，殊途同归。

### 3.4 落点

给写入类操作加一道"单写闸"：

1. **端口租约**：不是"探测到空闲就用"，而是"申请—占用—释放"三段式，释放失败要能自愈（进程被 kill 时锁要能被回收）。
2. **文件锁**：同一路径的写操作走跨进程文件锁，而不是靠约定"你别写我也别写"。
3. **提交串行**：所有"对外可见的变更"（改代码、改配置、写证据）排队过单一闸门。

判断标准很简单：**如果两个 worker 同时做这件事会互相污染，它就必须进闸门。**

## 4. 记忆：三条路线，先做最土的

### 4.1 三条路线各自的坑

| 路线 | 做法 | 主要缺陷 |
| --- | --- | --- |
| **向量 RAG** | 切块 → 嵌入 → 相似度召回 | 召回不可解释；更新是**追加**不是**修正**，旧结论会和新结论一起被召回，互相打架 |
| **结构化记忆** | 实体/属性/关系，写入时校验 schema | schema 僵化；写入成本高；遇到新类型就得改表 |
| **情景记忆** | 事件流 + 定期反思归纳 | 不做反思就只是日志；做了反思则要防"归纳出错误规律" |

三条路线不是三选一，是**配合**。但配合有顺序，顺序错了会白烧很多工程。

### 4.2 本项目已有的资产（比想象中多）

长期记忆目录现在已经是这个结构：

```
task.gotcha      813 条   踩坑与避坑知识
task.knowledge   461 条   领域事实
task.workflow    508 条   可复用流程
user.knowledge    22 条   用户分享的领域知识
user.narrative     1 条   用户讲述的经历
user.preference  110 条   用户偏好
```

这个分类**天然就是"反思归纳"的产物结构**：gotcha = 教训，workflow = 方法，knowledge = 事实。也就是说，情景记忆那条路线最难的一环（"从经历里提炼出什么"）已经有现成的收纳格。

所以结论是反直觉的：**不需要先引入向量库。** 先把"三类记忆 + 一条时间线 + 冲突消解"做扎实，收益远大于换技术栈。

### 4.3 三步走（按性价比排序）

**第一步：让记忆可以被"修正"，而不是只能被"追加"。**

现在的问题不是存不下，是**新旧结论会共存**。举例：某次记下"判分要用 `bool(mark_deliv)`"，后来发现这是 bug 改成三态——如果旧条目不被标记失效，下次召回就可能把错误结论又捞回来。

做法：
- 每条记忆带 `状态`（有效 / 已被取代）与 `supersedes`（取代了哪条）
- 写入前做**冲突检测**：同 domain + 同 point 的旧条目，默认进入"待取代"，而不是并列存在
- 关键：**取代关系要留痕**，可追溯"为什么改主意了"

**第二步：检索先做"土"的。**

不做向量，先做两块：
- **关键词 + 字段过滤**（domain / point / memory_type 都是结构化字段，能精确筛）
- **场景触发**（不是"每次都召回"，而是"遇到 X 类任务才查 Y 类记忆"）

判断标准只有一条：**记忆的价值 = 被召回且改变了行为的次数，不是存储条数。**
813 条 gotcha 如果从不被召回，那就是 813 条死重。所以第一步不是"再多存点"，而是"让它在该出现的时候出现"。

**第三步：反思归纳，但必须带证据。**

从情景流里提炼新条目时，强制携带引用（哪几轮、哪条 jsonl、哪个 sha1）。没有引用的归纳一律降级为"假设"，不进工作记忆。

这一条防的是最难发现的错：**归纳出一条听起来很对、但实际不成立的规律**，然后拿它指导后面几百轮。

### 4.4 顺带一提：记忆与规划是耦合的

记忆 2 分、规划 2 分，看起来是两个坑，其实是一个：**没有记忆的规划只能靠想象。**

规划器要估"这件事大概要多久"，靠的不是推理能力，是历史统计。这就是下一节的入口。

## 5. 预测式多尺度规划

### 5.1 多尺度：三个时间粒度

| 尺度 | 决策内容 | 现状 |
| --- | --- | --- |
| 秒级 | 这一条工具调用要不要发、参数对不对 | 有，但无预算概念 |
| 分钟级 | 这个子任务怎么拆、用哪个模型 | 粗放，靠固定阈值 |
| 小时级 | 这个目标还成不成立、要不要止损 | **完全没有** |

第三行是最大的空白。现在的系统能一门心思跑到 600 秒超时，却从不中途问一句"我还在往对的方向走吗"。

### 5.2 Meta-Thinker：每 N 步插一次目标复核

参照 Meta-Thinker 类做法，在长任务里每 N 步（建议 N=5~8，或每消耗 1/3 预算时）插入一次元认知检查，只问三个问题：

1. **目标还成立吗？**（原始诉求有没有被中途的偏差带跑）
2. **路线还是最优的吗？**（有没有更短的路被忽略了）
3. **要不要止损？**（剩余预算 vs 预估剩余工作量）

关键设计约束：**这个检查必须用便宜的方式做，且必须能给"停止"指令。**
- 用 14B 级（认知层），不用 30B——它只需要判断，不需要生产。
- 输出必须是结构化三选一：`继续` / `改道` / `放弃`，不允许输出长篇分析（长篇分析会把省下的钱花回去）。
- 每任务最多触发 3 次，超出强制走"放弃"分支，防止反复复核本身变成死循环。

### 5.3 用历史数据做预测基线（本项目特有的便宜办法）

这是本项目最容易摘的果子，也是我认为最值得做的一处创意：**评测台攒下的耗时数据，不该只当裁判，还能当预测先验。**

现有历史（145+ 轮真实样本，Python 主线）：

| 指标 | 数值 |
| --- | --- |
| 耗时 P50 | 69.5s |
| 耗时 P95 | 174.7s |
| 单发吞吐 | 约 5 tok/s（纯 CPU） |

由此可以立刻得到一个修正：**`--task-timeout 600s` 是拍脑袋的。**

按 P95 = 174.7s 计算，600s 相当于 P95 的 3.4 倍。这个阈值把大量"慢但会成功"的轮次记成了 `timeout`，直接污染了失败分桶——88 号 §8 里"4 路并行 2 路吃满 600s"其实就是这个错的直接后果。

正确做法是**让阈值由数据决定**：

```
合理超时 ≈ P95(同类任务) × k    （k 取 1.5~2.0）
```

而且 `P95` 应当**分桶查表**，不是全局一个数：

| 维度 | 为什么要分 |
| --- | --- |
| 语言 | Rust 编译成本远高于 Python，混在一起算没有意义 |
| 项目类型 | 涉及并发/中间件的任务天然更慢 |
| 第几轮 | 冷启动的第一轮明显慢于后续 |

落成一个查询表 `(语言, 项目类别, 轮次区间) → (P50, P95, 样本数)`，规划时先查表：

- 预估耗时 > 预算 × 2 → **直接拒绝或降级**（换更小的任务），而不是硬跑到超时；
- 预估耗时在预算内 → 正常执行；
- 实际耗时 > 预估 P95 × 2 → 触发 5.2 的目标复核。

这样规划、预算、止损三件事被同一份数据串起来了。**评测台从此不只是裁判，还是规划器的先验。**

### 5.4 注意：预测会自我实现

一个必须提前写下的警告：如果用预测值去设定超时，那么"预测得不准"会被机制放大成"确实做不完"。所以预测表要**定期用新批次重算**，且保留一部分"不设预测限制"的对照轮次，用来检验预测是否开始偏离现实。

## 6. 可验证化：G-V-R 与 Skills 沉淀

### 6.1 G-V-R 三要点

生成-验证-修订（Generate-Verify-Revise）看起来简单，落地有三个硬要求，缺一个就退化成"生成-自我表扬"：

| 要点 | 要求 | 违反的后果 |
| --- | --- | --- |
| **校验者独立** | 验证不能用生成它的同一个上下文 | 上下文里已经有"我刚写的代码很好"的倾向，验证会变成确认偏误 |
| **有轮次上限** | 最多 N 轮（建议 2~3） | 生成与修订互相拉扯，震荡不收敛，烧光预算 |
| **有客观锚点** | 校验依据必须是确定性的：`compile()` / `rustc` / 测试 / schema 校验 | 靠 LLM 自评 = 软尺子，回到 88 号 §5.2 的假绿事故 |

### 6.2 本项目的缺口：校验器装在了判分侧，不在运行时

现状：`compile_check` 已经有了，而且做得很干净（Python 用 `compile()`、Rust 用 `rustc --edition 2021 --emit=metadata`），但它**只在判分时跑**——也就是"事后量"。

该做的是把它**前移进执行循环**：worker 交代码 → 立刻本机编译 → 不过就把编译器原始报错回灌给 worker 重写（最多 2 轮）→ 还不过才算失败。

这个改动的性价比极高，理由：
- 编译器报错是**最便宜也最精确的反馈**，比让 LLM 自己找错便宜一个数量级；
- 直接打 `syntax-error` 那 24.8% 的桶；
- 复用已有代码，不需要新能力。

同时要立一条规矩：**回灌给 worker 的必须是编译器原文**，不能是"你的代码有语法错误，请检查"这种转述。转述会丢掉行号与具体原因，等于让模型从零猜。

### 6.3 Skills 沉淀：把成功路径固化

趋势上，成功的 Agent 系统都会把"反复用到的解法"从提示词里抽出来，变成可复用单元（本项目的 skills 机制、Claude 的 Skills、各家叫法不同）。

判据只有一条，且必须可量化：

> **同一类任务第二次做时，token 是否下降？**

不降就是没沉淀成功——只是把提示词换了个地方存放。这条判据要写进度量，否则"沉淀"会变成"堆文档"。

## 7. DeepSeek Super-agent 拆解

来源：2026-10-31 DeepSeek Harness 团队《Super-agent 设计探索：迈向更自主的 Agent 系统》，原型 `dsh-superagent-prototype`（MIT 开源）。

### 7.1 架构：Router + Worker

| 角色 | 职责 | 关键设计 |
| --- | --- | --- |
| **Router** | 常驻全局协调，接收群聊 / GitHub / 邮件等事件 | **只分派，不执行** |
| **Worker** | 独立上下文，并行做问题复现 / 代码审查 / 功能开发 | 可再调 Subagent |

一个很实用的细节：**Worker 接手任务后可以直接订阅后续消息**，不必每条都经 Router 转发。这减少了 Router 的转发开销，也让 Worker 能拿到连续上下文。

→ 对我们的启示：多 agent 交接现在靠自然语言，损耗大。让接手方**直接订阅**后续相关输入，比"再描述一遍背景"便宜得多。

### 7.2 存算分离与自愈

| 机制 | 做法 | 解决的问题 |
| --- | --- | --- |
| 存算分离 | 执行循环在云端，会话状态入库，本地只留轻量 daemon | 长任务不怕客户端断线 |
| **Watchdog** | 独立进程检测"无效循环"并尝试修复 | 死循环不是靠超时掐掉，而是被识别出来 |
| 异步 ReAct Loop | 执行耗时任务时仍能响应新指令 | 阻塞式执行会让系统"失联" |

→ 对我们的启示：**Watchdog 这个角色我们现在缺。** 眼下"卡住"只能靠 600s 超时兜底——这是最粗暴的方式（把"慢"和"死"混为一谈）。该有一个独立观察者，用**行为特征**（连续 N 步无进展、同一工具重复调用、输出长度趋零）判"无效循环"，而不是等时钟。

### 7.3 主动性与过滤

- **事件驱动 + 两级过滤**：程序规则快筛（便宜、可解释）→ 大模型慢判（贵、需要理解）。绝大多数事件在快筛层就被丢掉。
- **"静默复现并修复"**：确认问题真实存在、且找到简单修法，才提交；否则保持沉默。这条策略的价值是**压制噪音**——一个总在说话的 Agent 会很快被忽略。

→ 对我们的启示：这条和 4.3 的"检索先做土的"是同一个道理。**便宜的过滤在前，贵的判断在后**，顺序反了就是烧钱。

### 7.4 实测数据（值得记下的几个数）

负载设定：300 条消息、约 20 个工作请求。

| 指标 | 数值 |
| --- | --- |
| 半数任务完成时间 | 12.4 分钟 |
| 95% 任务完成时间 | 15.7 分钟 |
| 单会话子 agent 基准 P95 | 29.5 分钟（**且未调用子 agent**） |

最后一行的意思很值得玩味：在他们的基准里，**没调用子 agent 的简单会话反而 P95 更长**（29.5 分钟 > 15.7 分钟）。说明子 agent 不是开销，是**并行度来源**——分工把长尾削掉了。

压力测试：事件频率 1 → 40 条/分钟

| 指标 | 1/分钟 | 40/分钟 | 解读 |
| --- | --- | --- | --- |
| Router 批大小 | 1.0 | 2.8 | 自动攒批，说明批处理是天然的自适应 |
| 请求延迟 | 2.5s | 3.9s | 延迟涨幅远小于事件涨幅 → 系统有余量 |
| Router 决策数 | 基线 | +30% | 决策数没有线性爆炸，说明过滤有效 |
| 缓存 token | 23.23M | 31.77M | 成本随负载涨，但没失控 |

→ 最值得学的一点：**批大小随负载自适应（1.0 → 2.8）**。我们现在的并发是硬编码的（"2 路"是实测出来的经验值），完全可以改成按队列深度与推理队列状态自适应。

## 8. 落点排序：先做最便宜的

按"改动成本 ÷ 收益"排序，不按"看起来高级"排序。

> **排序公式（附录 A.4 之后补正）**：真实可修收益 = 桶大小 **×（归责归属为框架的比例）**。
> 一个 92 条但 100% 归模型的桶，可修收益是 0；一个 13 条的桶，可修收益就是 13。
> 按旧表（只看桶大小）排出来的第一名，恰好是完全不用做的那个。

| 序 | 动作 | 成本 | 直接收益 | 依赖 |
| --- | --- | --- | --- | --- |
| 1 | **超时阈值数据驱动**（P95 × k，分桶查表） | 极低（改配置 + 加查表） | 直接打 `timeout-no-output` 10 条 + 部分 `unverified` 13 条——**这是归责后唯一 100% 归框架的 23 条** | 无，历史数据已有 |
| 2 | **失败再分解闭环**（`delivered_code=False` → 拆任务/换角色/降粒度重试） | ~~低中~~ **已完成** | **唯一能碰那 86% 模型边界的框架手段**：单轮写不出就多轮写。可量化（可用交付率 89.4% 是否上升） | ✅ 已落地，见附录 A.6；待 `camp-g`/`camp-h` 出救回率 |
| 3 | **校验前移**（把 `compile_check` 放进执行循环） | 低（复用已有代码） | 原估计打 `syntax-error` 24.8% 的桶；**实测仅 17 条且全归 model**，见附录 A | 无，但须先修抽取器 |
| 4 | **记忆冲突消解**（状态 + supersedes + 取代留痕） | 中（动数据结构） | 让 813 条 gotcha 从死重变成可用的判断依据 | 无 |
| 5 | **单写闸**（端口租约 + 文件锁 + 提交串行） | 中 | 根治假红假绿，为真并行铺路 | 1、3 之后 |
| 6 | **Meta-Thinker**（每 N 步目标复核，14B） | 中高（需接第二个模型） | 小时级止损能力从 0 到 1 | 需要 14B 可用 |
| 7 | **多模型异构分层** | 高（模型下载 + 内存评估 + 三组对照长跑） | 质量与成本的帕累托改善 | 必须先有 1–6 的干净尺子 |

第 1、2 项可以立刻做，且都能靠现有数据量化效果。第 7 项必须最后做——**在没有干净尺子之前引入新变量，你永远说不清变化是谁带来的。**

原表里第 2 项是"校验前移"，排第 2 位的理由是"能打 24.8% 的大桶"。归责之后这个理由没了：
那 17 条 `syntax-error` 全部归 model，前移校验改变不了模型写错语法这件事，它只是让错误早点被发现。
**早点发现错误的收益是省时间，不是提高成功率——这两件事在指标上必须分开。**

## 9. 一页纸结论

1. **定位**：本项目是"能管住"的系统（可观测 5、治理 4），还不是"会变好"的系统（规划 2、记忆 2、自适应 2）。元认知超配，认知与记忆欠配。
2. **最该做的不是加强治理，而是把治理换来的信任花在认知与记忆上。**
3. **异构化成立但只是因为算力受限**，上了 GX10 集群要重估。裁判永远不能用 LLM。
4. **并行的敌人是共享可写资源**，不是并发数。探索无限并行，写入单一闸门。
5. **记忆先做"土"的**：能修正 > 能检索 > 能归纳。判断标准是"被召回且改变行为的次数"，不是存储条数。
6. **预测是暗线**。评测台的数据应当反哺规划器：超时阈值、是否拆解、要不要止损，全部由历史分布决定，而不是拍脑袋。
7. **可验证化最便宜，但要先把锚点钉牢**：编译器已经在手边，可锚点上系的是"抽取器抽到的文本"。抽错了，锚点就是假的，而它仍会自信地报成功——**71 条 `...`（Ellipsis 字面量）就是这么混过编译率的**（附录 A.5）。
   更麻烦的是假绿**不止一层**，且每修掉一层才看得见下一层：`...` → 空串 → 玩具代码（`print('Hello World')`，209 字符同一份模板被背了五遍）→ 最后是 `<code here>` 这类**假红**。最像真的那层恰恰最容易被当成"没问题"。
   一个必须记住的数：剔掉 102 条占位符后，编译通过率从 90.1% **涨到** 95.6%——**凡是真动手写的轮次，本来就大多能过。**
   先修抽取、再立"可用交付"这把尺，最后才谈前移。
8. **批量自适应**（DeepSeek 的 1.0 → 2.8）比硬编码并发数优雅得多，值得抄。
9. **靶心要乘归责权重，不能只看桶大小**（附录 A.4 的代价）：189 条失败里只有 23 条（12%）归框架，162 条归模型。按旧逻辑（桶大小排序）选出来的第一名 `placeholder` 92 条，100% 归模型，**改了不会有任何变化**。这是本项目最贵的一次"差点走错"。
10. **感知不等于行动，这是系统最实的缺口**：worker 每轮都在 `payload` 里诚实报告 `delivered_code=false`，框架收到后什么也没做——只会试到超时或背模板，然后如实记下来。G-V-R 缺的不是验证器，是**验证不通过之后的下一步**。既然单轮写不出来，就让它多轮写。
    **（已接上）** 分解重试已落地：双条件判据、只做两轮、按上轮有无骨架分"接力补全 / 降粒度"两条路；三本账分开、派生文件在装载时拦掉、`timeout-no-output` 不进实验组；`selftest` 21→34 项，门禁 26/26 无回归。但**"接上了"不等于"有效"**——救回率要等 `camp-g`（开）对 `camp-h`（不开）跑出来。这个实验的价值不是提高成功率，是给"能力不足 vs 一次要不完"这个二选一提供判决。
11. **21% 的占位符，更像"一次要得太多"，不像"能力不足"**。旧尺子把这两件事量进同一个桶（`placeholder` 92 条），于是修法也跟着错——它会被导向"换更强模型"，而真实需要的是"改任务形状"。
    区分它们的成本很低（一个开关跑两组），不区分的代价是**永远在给错的病下药**。这条可以推广成一条通则：**当一个失败桶里混着两种病因时，先做分辨实验，再做修复方案。**
12. **选型原则（比任何架构选择都重要）**：做 Agent 项目，先问这个任务域**有没有免费的客观锚点**。
    能编译、能跑测试、能对拍数据——有，自进化才可能；纯生成、纯评价、纯文风——没有，所谓自进化就是自己给自己打分。
    本项目真正领先于公开实践的地方只有一处：**判分有客观锚点且可重放**。架构可以换，尺子换不了——换了尺子，之前所有数据全部作废。
13. **判断器本身也要被检验，否则它会安静地错下去。**
    这条是上面所有教训的上一层。判分器出过错（A.1–A.5 共五层假绿），我们给判分器补了证据留存与重放；但**归责器**——决定"这一刀该不该切"的那个函数——从来没被验证过。它一旦系统性偏，后面每一个"下一刀"都会指向错的地方，而且看起来很有依据，因为它是所有分析的入口。
    现在 `evolve.py --selftest` 用三类样本给它做体检：**正样本**（该判框架的别漏）、**负样本**（模型能力边界别错怪给框架）、**反例**（同形不同因的两件事别判成一件）。首跑 15 项，当场抓出两处——一处是我构造的样本不合真实数据形状（真实成功轮必带 `status/done/delivered_code` 三件套），另一处是真的判据盲区：**取数失败时 `steps/agents` 也是 0，与"流程根本没起来"完全同形**（A.7 的 r249 就是活证据：`elapsed=287s` 说明任务跑满了，只因为最后一步查询 401 就被记成"框架没跑起来"）。
    于是多了一个 `framework-collector` 子类：**该修的是客户端取数与续期，不是后端启动。** 不分开，就会拿"客户端 bug"的证据去改后端。
    > 通则：**任何用来做判断的东西，都要能被一组已知答案的样本打回原形。** 判分器、归责器、门禁、验收脚本，一个都不能例外。给尺子做体检的成本是十几行断言，不做体检的成本是全部结论作废。

> 最后一句留给纪律：趋势里最容易被误用的词是"更自主"。
> 自主的前提是**能验证**；不能验证的自主，只是把错误做得更快。

## 附录 A：写作当天的实证——35 条假绿的解剖

这篇文档正文写完后，当晚给判分器补了一刀（占位符识别 + 语言猜错隔离）。
结果值得单独记一节，因为它把正文里几条抽象原则变成了带血的数字。

### A.1 发生了什么

对 233 条"有完整证据"的样本按当前判据重算，**48 条翻案**：

| 方向 | 条数 | 原文 | 说明 |
| --- | --- | --- | --- |
| `True → None` | **35** | `'...'` | Python 里 `...` 是合法的 Ellipsis 表达式，`compile("...")` **成功** |
| `False → None` | 13 | `<code here>`、`<你的代码>`、`... (your full code here) ...` | 送去编译必然 SyntaxError |

也就是说：过去报表里那 35 条"编译通过"，代码原文只有三个点。

### A.2 分桶因此整体改写

| 桶 | 修正前 | 修正后 |
| --- | --- | --- |
| `syntax-error` | 56 条（第一大桶） | **11 条**（其中 rust 8、python 3） |
| `placeholder-instead-of-code` | 不存在 | **48 条**（占可复验子集 18.2%，第一大桶） |
| `legacy-unverified` | 不存在 | 33 条（旧口径残留、无证据可复算，不参与决策） |

编译口径同时纠偏：**275/324（84.9%）**，分母只含"可判定轮"；
其中证据在手、能被当前尺子复算的 **可复验子集 264 轮**，跨代比较只认这一档。

### A.3 三条教训

**一、假绿比假红更危险。**

假红会让数字难看，人不爽，于是去查；假绿会让数字好看，人满意，于是什么都不会发生。
35 条假绿静悄悄躺了很多轮，一直在替"编译通过率"抬轿子，没有任何人会觉得它有问题。

这直接对应正文 §6.1 的第三要点：**验证必须有客观锚点**。
我们以为自己有（编译器），但锚点上系着的是"抽取器抽到的文本"——
抽取器抽错了，锚点就是假的，而它仍然会给出自信的成功。

**二、假红和假绿永远同源。**

它们的根都不是"编译逻辑错"，而是"抽取器抽到了非代码内容"。
修一个判据，两个方向同时收敛——这就是为什么正文 §8 里"校验前移"的收益被高估了：
在抽取器不可靠的前提下，把编译校验挪到执行循环里，只会让假绿更早发生。

**顺序应该是：先保证"验的是真东西"，再谈"什么时候验"。**

**三、靶心必须由尺子回答，不能由直觉回答。**

修正后的靶心完全变了：

- 旧桶指向"提示词里的语法约束不够"→ 会去调提示词格式要求；
- 新桶指向"**模型压根没写代码，只吐了模板占位符**"→ 要硬性禁止占位符、给反例、必要时判失败重来。

如果只看旧桶就开干，会花一周去修一个只剩 11 条的问题，而真正占 18.2% 的问题一动没动。

> 这是 88 号"下一次修改必须由尺子指出来"那条纪律的第一次真实兑现。
> 尺子本身也会错——所以它必须可复算、可翻案、留证据。留证据不是为了审计，
> 是为了**允许自己推翻自己**。

**补注（同一夜的第二次打脸）**：上面这条写完不到一小时，「新靶心」自己也被推翻了。
分桶确实指出了"哪里失败最多"（`placeholder` 92 条），但它**没有回答"这个失败该谁负责"**。
补上归责之后再算，92 条全部记在模型头上，框架能修的只有 23 条。详见 A.4——
**尺子能告诉你哪里疼，不能告诉你该找哪个科。**

### A.4 同一夜的第二次与第三次翻案：假绿还有第三层，靶心还要再换一次

A.1 修掉的是"没内容"（`'...'`）。修完之后还剩 26 条"明确没有交付却判成编译通过"的样本，
逐条看原文，出现了**第二种假绿，而且比第一种健康得多**：

- 空串——`compile("")` 通过；
- `print('Hello World')`、`import os`——**语法完全合法，只是与任务毫无关系**。

其中那串 `print('Hello World')` 在五个不同轮次里反复出现，**长度一模一样（209 字符）**。
同一份模板被背了五遍。

**这一层的可怕之处**：上一层的 `'...'` 一眼就可疑，这一层看起来完全正常——
格式对、语法对、能跑，只有"内容和任务无关"这一条不对。纯靠语法尺子永远抓不到它。

#### 第三把尺子：可用交付

样本里其实一直有个信号没人用——`delivered_code`，worker 自己报交没交付：

| delivered_code | n | 代码长度 P50 | 编译通过 |
| --- | --- | --- | --- |
| True | 311 | **1352** | 310 True / 1 False |
| False | 132 | **7** | 14 False / **21 True** |

两组几乎完全可分。那 21 条"能编译"的，全部落在 `False` 组里，全是玩具代码。

于是主尺改为 **可用交付（usable）= worker 认领 `delivered_code=True` 且本机语法通过**：

| 口径（可复验子集 350 轮） | 数值 |
| --- | --- |
| 编译通过率 | 335/350（95.7%） |
| **可用交付率** | **313/350（89.4%）** |
| 落差 | **6.3 个百分点** |

那 6.3 个点，就是"能编译但没人认领"的虚高。**一个只问"能跑吗"的判分器，是能问出的最弱的问题。**

#### 第四步：从"哪里错最多"走到"该谁负责"

分桶表把 `placeholder` 92 条排在第一位，按它的指引下一步该去改提示词。改之前先问了一句：
**这 92 条，是框架的问题吗？**

把 189 条失败与 413 条成功逐项对照框架行为：

| 组 | n | steps | agents | 交接 | tokens P50 | elapsed P50 |
| --- | --- | --- | --- | --- | --- | --- |
| 成功 | 413 | 全是 4 | 全是 3 | 1239（3.0/轮） | 937 | 112s |
| 交不出东西 | 189 | 全是 4 | 全是 3 | 537（2.84/轮） | 607 | 185s |

**两组的框架行为完全一致**：步骤一样、agent 数一样、交接率几乎一样。
差别只有两处——失败组吐的字少 35%，花的时间多 65%。

一条具体样本：`P10 任务队列 r215`，`status=succeeded`、`steps=4`、
`agents=[super-agent, code-agent, guard-agent]`、`handoff=3`、`tokens=604`、`elapsed=219.63`、
**`code_chars=3`**。四步跑满、三个 agent 全到场、交接三次，最后交出来的是 `...`。
而它自己的 payload 里明写着 `delivered_code: false`、`summary: ""`——**worker 一开始就知道自己没交。**

归责结果：

| 归责 | 判据 | 轮数 |
| --- | --- | --- |
| framework | steps/agents 为 0，或输出取不全 | **23** |
| model | 流程跑满四步仍写不出东西 | **162** |
| unknown | 旧口径残留、证据不在 | 33 |

**162 : 23。**

框架能修的只剩 12%：10 条 `timeout-no-output`（steps=0，600s 内一步没走，多半是并发抢 CPU）
+ 13 条 `unverified`（tokens P50=1255，全样本最高，却取不全代码，是输出通道截断）。

剩下 86% 是模型能力边界。`placeholder` 92、`stub-pass` 24、`no-code-at-all` 25、
`syntax-error` 17——全部记在 model，**改框架一个数都不会动**。

#### A.4 的三条教训

**一、假绿是分层的，而且最后一层最像真的。**

`'...'` → 空串 → 玩具代码，三层。每修掉一层才看得见下一层。
最像真的那层（`print('Hello World')`）恰恰是最晚被发现、也最容易被当成"没问题"的。

顺带印证正文 §6.1：**验证的锚点上系着什么是关键**。这里锚点上系着的是
"抽取器抽出来的那段文本"，而文本本身可能是对的、只是无关。
**格式与语法都通过了，任务却没被完成——这是最像成功的失败。**

**二、分桶回答"哪里疼"，归责回答"该谁治"。少后者会把整年花在改不动的地方。**

`placeholder` 92 条占 14.7%，是最大的桶；但它 100% 归 model。
只看桶的大小去排序，下一步就是改提示词，改完数字纹丝不动，
接着会以为"改得不够狠"，再改第二轮、第三轮——**很忙，很累，没进步。**

这直接改写正文 §8 的落点排序：**"收益大小"必须乘上"归责权重"再排序**。
一个 92 条但不归你管的桶，实际可修收益是 0；一个 13 条的桶，可修收益是 13。

**三、感知到了不等于会行动——这是本系统最实的一个缺口。**

`delivered_code=false` 一直写在 payload 里，worker 每次都在诚实地报告"我没交"。
但框架拿到这个信号之后**什么也没做**：它只会试到超时，或者退化成背 hello world，
然后把实情记下来，结束。

这正好是正文 §6 和 §5 都点到、却一直没落地的能力：
**G-V-R 缺的不是验证器，是"验证不通过之后的下一步"**。校验到位了，重试策略是空的。
所以真正该做的不是在判分侧继续加尺子，而是在运行时补上一条最小闭环：

> 拿到 `delivered_code=False` → 触发任务再分解 / 换角色 / 降粒度 → 重跑一次，
> 拿两次里较好的那次。

这条闭环完全是框架侧的、可量化的（可用交付率是否上升），
而且它恰好绕开了那个改不动的 86%——**既然单轮写不出来，就让它多轮写。**

### A.5 第二天：第五层假绿，和一次必须自我更正的口径错误

写 A.1 时有个地方我不够严谨，先更正：

> A.1 表格里写"原文 `'...'`"，那个引号是 **Python repr 的引号，不是代码里的引号**。
> 真实代码就是三个字符：`...`。

这件事必须说清楚，因为它不是笔误，而是**归因错了**：

| 写法 | 是什么 | `compile()` |
| --- | --- | --- |
| `'...'`（带引号） | 一个字符串字面量 | 通过（合法常量表达式） |
| `...`（不带引号） | **Ellipsis 字面量** | 通过（合法常量表达式） |

两者都能过编译，但含义完全不同。A.1 当时的叙述是"被当成字符串了"，听起来像个抽取器 bug；真相是**它本身就是合法语法，抽取器一个字节都没抽错**。

这个区别决定了修法：如果是抽取器 bug，改抽取；如果是合法语法，只能改判据——**必须能识别"语义上是占位符"的字符串，而不能只问"语法上合不合法"**。

#### 一个意外的旁证：编译器自己招了

翻长跑的 stderr 时看到这样一行，来自 camp-e 的某次 `compile()`：

```
<soak>:1: SyntaxWarning: 'ellipsis' object is not callable; perhaps you missed a comma?
```

这行是 **Python 解释器自己给出的定性**：它认得 `...` 是 Ellipsis 对象，所以在看到 `...(...)` 这种写法时，它会提醒"你漏了逗号吧"。

这行警告的价值有两层：

- 它**坐实了**「`...` 是合法表达式」这个判断——解释器不但没报错，还继续编译下去了；
- 它同时说明模型写的不是单纯的 `...`，而是 `...` **后面还跟着调用**（可能是 `...(your code here)` 这类）。**模型是在用省略号假装"这里有一大段"**，而 Python 把它读成了一个被调用的 Ellipsis 对象。

一件事用两种方式被证实了：判分器重放（102 条）和编译器 stderr（这行警告）。这也说明**stderr 一直在写，只是没人读**——和 A.4 里"`delivered_code` 一直在报，只是没人用"是同一个病：**信号不缺，缺的是有人看。**

#### 再翻一次案：102 条

新批次（camp-e / camp-f，均带完整证据）跑完后重放，**481 条可重放样本里 102 条结论变了**。逐条抽原文核对，形态分布如下：

| 原文形态 | 条数 | 原判定 | 性质 |
| --- | --- | --- | --- |
| `...` | 56 | True | **假绿** |
| `...\n...` | 14 | True | **假绿** |
| 半截 Rust（`"use axum::{"..."`） | 1 | True | 假绿（语言猜错） |
| `<code here>` | 12 | False | **假红** |
| `<你的代码>` | 8 | False | **假红** |
| `<修改后的代码>` | 3 | False | **假红** |
| `... (your full code here) ...` | 2 | False | 假红 |
| `... (完整代码)` | 1 | False | 假红 |
| 半截 Rust（另一条） | 1 | False | 假红 |

**71 条假绿 + 31 条假红 = 102 条，全部同源：根本没写。**

这是 A.3 第二条"假红和假绿永远同源"的第二次验证，而且规模更大。上一次是 48 条里 35+13，这次是 102 条里 71+31——**同一个根，两个方向，比例几乎一样。**

#### 31 条假红比 71 条假绿更值得说

假绿让指标虚高，至少"看起来好"；假红让指标虚低，而且**它伪装成"能力不足"**。

`<code here>` 送去编译必然 SyntaxError，于是报表上记一笔 `syntax-error`。报表读起来是："模型连合法语法都写不出来。"

真实情况是："模型连一个字都没写。"

这两句话对应的修法完全相反：
- 若是前者 → 换更强模型、加语法提示、前移校验；
- 若是后者 → 降粒度、硬性禁止占位符、改任务形状。

**假红的危害不是数字难看，是它会把你指向错误的药。** 这比假绿更贵，因为假绿只是让你懈怠，假红让你误诊。

#### 修完之后的那个反直觉的数

| 口径 | 编译通过 |
| --- | --- |
| 旧（占位符算结论） | 437/485 = 90.1% |
| 新（占位符不算结论） | 366/383 = **95.6%** |

**踢掉 102 条垃圾，通过率反而涨了 5.5 个百分点。**

通常"清脏数据"会让人预期数字变难看，这里反过来——因为占位符里 31 条原本被判"编译失败"（拉低分子）、71 条被判"编译通过"（撑大分母）。两类垃圾合力把比例压到 90.1%。真实情况是：**凡是真动手写了的轮次，95.6% 都能编译通过。**

所以真正的问题从来不是"模型写不对代码"，而是"**21% 的轮次根本没打算写**"（camp-e 53/239、camp-f 49/246）。

这个发现改变了 A.4 归责结论的读法：那 92 条 `placeholder` 记在 model 头上没错，但它不是"能力不足"，更像"**一次要得太多，就只回三个点**"。能力不足要换模型；一次要不完要改任务形状。

**两件事的修法完全不同，而旧尺子把它们量成了同一个桶。**

金句留在这里：**最安静的失败，是那种语法完全正确的失败。**

### A.6 闭环落地：从"感知到了"到"做了点什么"

A.4 结尾留下的那条闭环（`delivered_code=False` → 再分解 → 重跑一次），当天就接上了。设计上只做了三个决定：

| 决定 | 内容 | 依据 |
| --- | --- | --- |
| 判据用两个条件 | worker 认领交付 **且** 本机能编译 | 只用"能编译"会被玩具代码骗（A.2）；只用"认领交付"会被自述骗（A.4 的 34 条"本机无法复验"） |
| 只做两轮 | 不做三轮 | 第三轮的边际收益还没有数据支撑，先引入就是给尺子加噪声 |
| 按上轮残留分两种打法 | 有骨架（≥120 字符）→ **接力补全**；无骨架 → **降粒度**（只写一个核心函数） | 从零重写最常见的退化是背模板（同一份 209 字符 hello world 出现五次）；2B 整包交付几乎必败，但"写一个函数"在它的量级上 |

工程上三条克制，每条都对应过一次教训：

1. **三本账分开**（主样本 / `-retry` / `-decomp`）。开一个实验开关，不该让任何历史口径变一个字。
2. **`load_samples` 里拦掉派生文件**。这是个差点踩进去的坑：`-retry` / `-decomp` 同样命中 `*.jsonl`，而 tag 与主批次不同（`camp-g-retry` ≠ `camp-g`），`(tag, round)` 去重**拦不住**——放进来就是样本量虚增、成功率虚高。**"新加一列数据"和"新加一个样本"必须分清。**
3. **排除 `timeout-no-output`**。那是 steps=0、框架侧没跑起来，分解只会再白等 600 秒。这批要用超时阈值治（§8 第 1 项），不该混进"模型能不能多轮写出来"的实验。

`selftest` 从 21 项扩到 34 项，正负样本都测（两个条件的四种组合、两条打法、三种结论）。**只测"该重试的都重试了"，一个永远返回 False 的函数也能全绿**——这条教训 A.1 已经吃过一次。

同日全量复跑门禁：**26/26 PASS、负向演练 8/8 按预期变红**，确认这一改动无回归。

**但这一条现在只能算"接上了"，不能算"有效"。** 验证方式是 `camp-g`（开 `--decompose`）对 `camp-h`（不开），同轮数同任务流，看 `evolve.py --decomp` 报出的救回率：

- 救回率显著 > 0 → 说明那 21% 是"一次要太多"，往"改任务形状"方向继续投；
- 救回率 ≈ 0 → 说明是"真不会写"，那就只能换模型（§2），别在框架侧再花力气。

**这个实验的价值不是提高成功率，是给"能力不足 vs 一次要不完"这个二选一提供判决。** 在此之前，所有相关讨论都只是在猜。

### A.7 第七次核查：我自己也犯了"看栈归因"的错

这一节记的不是一个发现，是**一次被我自己的数据当场打脸的推断**。留下它，因为它比发现本身更有用。

#### 我一开始怎么想的

翻 `.err` 时看到两边都躺着同一段栈：

```
Exception in thread Thread-2 (_readerthread):
  File "...\subprocess.py", line 1597, in _readerthread
    buffer.append(fh.read())
UnicodeDecodeError: 'gbk' codec can't decode byte 0xab in position 110
```

我立刻写出了一条"很像那么回事"的因果链：

> 起子进程没指定 `encoding` → Windows 默认 GBK → worker 一输出中文读线程就死 → 这一轮 stdout 再也不会被读 → 抽取器拿不到代码 → `code=-`、`agents=0` → 判分器记成"框架没跑起来"。

链条完整、术语对、还能对上 camp-e 的 r248/r249 那两行 `st=None agents=0`。**差一点就写进文档了。**

#### 数据怎么说

把 camp-e（255 轮 / 7 条异常）和 camp-f（260 轮 / 6 条异常）的 13 条逐条摊开看字段：

| 类型 | 条数 | 关键字段 | 真实含义 |
| --- | --- | --- | --- |
| `timeout-no-output` | 5（e:67/125/161/248，f:71） | `status=None`、`agents=0`、`elapsed=600.0`、`note={'_err': 'TimeoutError: timed out'}` | 请求吃满 600s 超时，**没有任何返回** |
| 令牌过期 | 1（e:249） | `status=None`、`agents=0`、`elapsed=287.11`、`note='访问令牌已过期'` | 任务真跑了 287 秒，**查详情时失败** |
| `no-code-at-all` | 7（e:112/238，f:40/76/94/130/202） | `status=succeeded`、`agents=3`、`steps=4`、`code_chars=0` | 模型跑完了，**没写代码**——模型侧问题 |

**GBK 和这 13 条一条都不沾。**

读线程所在的那处 `subprocess.run` 只有一个用途：Rust 代码的 `rustc --edition 2021 --emit=metadata` 编译检查（`text=True`，无 `encoding`）。它发生在**判分阶段**，那时代码早已拿到手。它最坏的效果是让 rustc 的 `stderr` 丢掉、`compile_detail` 退化成 `rc=N`，**不会让 `code=-`、`agents=0`**。

而且现在跑的是 `--suite py`，这条路径本来就不走。

**结论：栈是真的，因果是我编的。**

#### 顺手挖出的真缺陷：状态码被 `_` 吞掉了

顺着 r249 那条 `elapsed=287.11` 往下查，在 `run_task()` 里看到这一行：

```python
_, detail = authed_call(base, "GET", f"/api/v1/tasks/{task_id}", timeout=60)
task = task_of(detail or {})
row["task_status"] = task.get("status")
```

**HTTP 状态码被 `_` 直接丢了。**

于是链条变成：查询失败 → `detail` 是 `{"detail":"访问令牌已过期"}` → `task_of()` 取不到任务 → `task_status=None`、`agents=0`、`code=0`。

而这组取值，和"任务根本没跑起来"**完全同形**。

r249 是唯一被我逮到的实例：它 `elapsed=287.11`——**任务明明真跑了 287 秒**，却因为最后一步查询失败，被记成了"框架没跑起来"。

这一条的意义比 GBK 大得多：**"同一症状、两种病因"不只发生在模型侧（A.5 的占位符），也发生在框架侧。** 而且框架侧这一例更隐蔽——它连 `note` 里那句"访问令牌已过期"都只是碰巧留下的，如果后端换一句提示语，这条线索也会消失。

#### 我错在哪，为什么值得记

三个错叠在一起：

1. **看到栈就归因**。栈只证明"某处出过异常"，不证明"这条异常导致了那个结果"。我把相关性当成了因果。
2. **没验证就写**。这条推断差一步就进文档了。如果写进去，读者会花时间去改一个（真实存在但无害的）`encoding`，而真正的洞——丢状态码——会继续漏下去。**这正是 A.3 那句"假红会把你指向错误的药"的第三次复现，这次犯错的是我。**
3. **犯的错和这套系统犯的错是同一个**：`_, detail` 是把"查询失败"当成"没有状态"；我是把"看到异常"当成"知道原因"。**都是把"没读到"说成"没有"。**

#### 三处修法

| # | 位置 | 改法 | 收益 |
| --- | --- | --- | --- |
| 1 | `run_task()` 查详情 | `d_st, detail = authed_call(...)`；非 200 记 `detail_http` 并在 `note` 写明，不再静默降级 | 让"查询失败"和"任务没跑"永远能分开 |
| 2 | `compile_check()` rust 分支 | `subprocess.run(..., encoding="utf-8", errors="replace")` | rustc 的 stderr 不再丢，`compile_detail` 恢复可用 |
| 3 | 令牌续期 | 查询详情前也过一次 `ensure_fresh`，而非只依赖 `authed_call` 的 401 重试 | 长跑跨 TTL 时不再整轮报废 |

第 1 条是主修，第 2、3 条是顺手。**注意第 2 条的定位要诚实：它修的是诊断质量，不是成功率。**

> 一个方法论上的收获，比这三处修法都重要：
> **验收一条推断，要问"如果是这样，哪些数字会不同"。**
> 我当时如果先问这一句，就会发现"GBK 只影响 rust 路径，而这批是 `--suite py`"——一句话就能否掉整条链。
> 反过来，A.5 那条 Ellipsis 判断之所以站得住，正因为它经得起这一问：102 条翻案的原文、编译器警告、通过率从 90.1% 涨到 95.6%，三个独立证据指向同一件事。

### A.8 第八次核查：改对了，但没接上

修完 A.7 那三处，我做了三件事，全部"通过"：`run_task()` 补了 `detail_http` 记录、`evolve.py` 加了 `framework-collector` 归责、自检 15 项全绿。看起来这条链已经通了。

**没通。** 断在最不起眼的一环：`run_task()` 把 `detail_http` 放进返回字典，但 `judge()` 负责把返回压成一行可统计样本，它的字段清单里没有 `detail_http`。所以这个值在落盘前就被丢掉了。`blame_of()` 读一个永远不存在的字段，`framework-collector` 永远不会触发。

恶劣之处在于**失败是静默的**：报表照常输出，`framework` 那行照常显示，只是所有取数失败都伪装成了"流程没起来"。看上去像是"这个 bug 已经不存在了"，实际上是"检测它的传感器没接电"。如果没有顺手 grep 一遍写入路径，这条链会一直"修好了但没生效"。

于是补了两处：`judge()` 透传 `detail_http`；`failure_reason()` 在超时判断**之前**先判 `collect-failed`，让桶名自己说明真因（桶名是给人看的，`timeout-no-output` 这个名字会把下一刀引向超时阈值和吞吐）。

> 通则：改数据管线时，改动点要三处对齐——**造的人写了、传的人带了、读的人认了**。缺任何一处都等于没改，而缺第三处最危险，因为报错不会发生、数字不会消失，只是解释错了。

### A.9 顺便发现的无效实验：`unverified` 不该进分解组

`camp-g` 是"开分解"对"不开"的对照实验，判分解到底能不能救回。跑到 34 轮时出现两组可疑样本：

| 轮次 | 首轮 | 二轮 | 说明 |
| --- | --- | --- | --- |
| r2 | `unverified`，code=3293 | `syntax-error`，code=802 | 首轮写了 3293 字符，只因 output 被平台截断、本机复验不了 |
| r3 | `unverified`，code=3172 | `syntax-error`，code=116 | 同上，重写后只剩 116 字符 |

问题很清楚：`unverified` 的含义是"**写了，但取不全，无法复验**"，不是"没写出来"。把它当成失败送进分解，等于让模型把一条已经写好的完整实现重写一遍——而实测重写结果比原来差一个数量级。**这不是"分解没用"，这是拿错了样本。** 若不清洗，这 2 例会以"分解失败"的身份进统计，把救回率往下拉，进而支持"多轮没用"这个错误结论。

这正是 A.7 那个错的同一个形状：**取不到 ≠ 没有**。上次犯在归因上，这次犯在实验分组上。

修法是把它和 `timeout-no-output` 一样排除出实验组——两者都不是"模型多轮能不能写出来"的证据，一个是框架没启动，一个是取数不完整，都属于"实验装置坏了"而不是"被测对象不行"。

同时 `camp-g` 里出现了第一次真救回，值得记下：

| 轮次 | 项目 | 首轮 | 二轮 | 判决 |
| --- | --- | --- | --- | --- |
| r31 | P9 微服务接口 | `placeholder`，code=3 | 成功，code=1236，369s | **rescued** |

清洗后的账：有效分解 6 例，救回 1 例（r31，来自"降粒度"路径），其余 5 例 `still-bad`（其中 r17 两轮都是占位符，降粒度也没用）。样本还太小，不下结论；但"分解完全无效"这个假设已经可以排除了。

> 通则：**实验组要清洗掉"装置故障"，否则你测的是自己的手抖。** 判据是问一句：这批失败如果装置是好的，它还成立吗？

### A.10 第十层假绿：`...` 能编译；以及"语法错"桶里其实只有一个是语法错

A.5 记过一个现象：那 102 条垃圾里，31 条原本被判"编译失败"、71 条被判"编译通过"。当时只知道这些结论不对，没查明**它们凭什么能编译通过**。而 A.5 的修法是在**报表层**把占位符剔除，落盘的 `compiles` 字段仍然写着 `True`——报表干净了，源头还脏着。这一节补上机制，也把修补从报表挪回源头。

（下面所有数字都在"落盘样本去重 261 轮"的口径上重算，与 A.5 当时的分母不同，看趋势别看绝对值。）

**先证伪一个我们内部流传的猜测：把 `syntax-error` 归因于 `max-tokens` 截断。** 14 条 Python `syntax-error` 的 tokens 分布是 `min=579 / P50=624 / max=856`，离任何常见上限都远；代码尾部 13/14 是自然收尾，没有一条悬在括号或逗号上。模型不是被掐断的，它是主动只写了这么点。

**真正的信号是长度**：`code_chars` 的 `min=6 / P50=11 / max=410`。一段"语法错误"的代码，正文中位数只有 11 个字符——这个长度连语法都装不下，说明这批样本里几乎没有语法错误。

按内容重新分类后，14 条 Python 样本是四种完全不同的病：

| 病因 | 条数 | 实例 | 该做什么 |
| --- | --- | --- | --- |
| 纯占位符 | 4 | `<code here>`、`<你的代码>`、`<修改后的代码>`、`... (your full code here) ...` | 改提示词：要求真给代码 |
| 语言判错 | 2 | `"use axum::{"..."` —— Rust 片段被按 Python 编译 | 查围栏标注与嗅探规则 |
| 真·不完整 | 2 | `def parse_date(...):` 省略号当参数；函数体内只有 `# TODO` | 降粒度：只要一个函数 |
| 提示词回显污染 | 1 | 代码第 16 行起粘着「这段代码没通过检查，错误信息：…」 | 修拼接：诊断文本不能进代码字段 |

第四类值得单独说：那条样本的"代码"里，前 15 行是正常实现，第 16 行开始直接粘着上一轮的诊断提示词。**修复轮把错误文本拼进了 prompt，模型又把 prompt 当成了代码的一部分输出。** 这是一个自污染回路——轮次越多，喂回去的上下文越脏，最后模型是在写"我对上一轮的检讨"，而不是在写程序。这也给"多轮修复"划了一条边界：**每一轮只准回灌代码和一行诊断，回灌整段对话就是在培养复读机。**

**然后是这轮最大的发现。** 把 `...` 当占位符剔除后重放历史，`compiles=True` 从 217 条掉到 179 条，**虚高 17.5 个百分点**。被剔除的 38 条里，37 条正文就是 `...`（三个点，3 字符）。

原因很简单：`...` 在 Python 里是合法表达式（`Ellipsis` 字面量），`compile("...")` 不报错。于是模型一个字没写，判分器却盖了"编译通过"的章。用 `--rejudge` 重放才看见——**落盘留了 `code_full`，这个错误才暴露；它在此前所有摘要报表里都是隐形的。**

但更重要的发现在下一层：**这 38 条一条都没进"可用交付"**。因为 `usable_of()` 要求 `delivered_code is True 且 compiles is True`，而 `...` 这类样本的 `delivered_code` 是 False。所以重算之后可用交付率 63.6% 一动不动。

同一次故障，污染了两个指标里的一个。这给出选指标的一条硬标准：

> **挑指标时，问它最烂的输入能不能通过。** 编译率被 `...` 骗过去了，交付率没有——因为后者要求"模型认领交了、且本机验得过"同时成立，空交付连第一件都过不去。指标的价值不在"能算出来"，在"算不出来的时候它会挡住你"。

反过来说，这也解释了为什么此前的结论方向一直没错：编译率虚高 17.5 个百分点，但主结论看的是可用交付，它没被这层假绿污染。**尺子有一根刻度坏了，恰好坏的不是我们看的那根。** 运气好不等于做对了——如果当时把编译率写进 KPI，这一轮的方向早就跑偏了。

至此假绿挖出十层，从"假红假绿同源"到"`...` 能编译"，一层比一层更接近"什么都没做但看起来做了"的本质。而十层里有六层是靠**留存原始证据 + 用新尺子重放**才浮出来的，靠看摘要报表一层都看不见。这也是 A.6 那个闭环里最不该省的一环：报表是给人看的，证据是给下一版尺子用的。

#### 重排靶心：`syntax-error` 塌了，露出真正的第一名

把占位符从语法桶里拿出来之后，740 轮的口径变成这样（可复验子集 593 轮）：

| 原因 | 轮数 | 占可复验子集 | 归责 | 语言 |
| --- | --- | --- | --- | --- |
| `placeholder-instead-of-code` | 113 | 19.1% | model | **全部 python** |
| `stub-pass`（能编译但无关的玩具代码） | 22 | 3.7% | model | python |
| `syntax-error` | 21 | 3.5% | model | **rust 17 / python 4** |
| `unverified`（取了但取不全） | 15 | 2.5% | framework | python |
| `timeout-no-output` | 11 | 1.9% | framework | — |

**Python 真正的语法错只剩 4 条。** 之前那个"28 条 Python syntax-error、怀疑截断"的靶心，是被占位符冒充出来的——桶一大半是空的，还立了个牌子说"此处有语法问题"。如果照着它去调 `max-tokens`、去改围栏标注，改完一个字都不会动。

而 `syntax-error` 剩下的 21 条里 17 条是 Rust。这也对得上：本轮跑的是 `--suite py`，Rust 样本本来就少，能留下来的自然都是硬错。**主战场不是它。**

真正的第一名是 `placeholder`，113 条，全部 Python，而且全部落在四个项目上：P10 任务队列 44、P6 API 文档生成 28、P9 微服务接口 27。这个分布不是随机的——**它们都是"要交付一整个可运行模块"的任务**，而 P5 日志聚合、P8 数据清洗这两个项目一次都没进过这个名单。

于是 A.4 定下的那条规矩需要一次修正。A.4 说：靶心要乘归责权重，`placeholder` 归 model，改框架无用，所以别切它。这个推理每一步都对，但结论错了，因为它默认了归责只有两类：

> **framework**（流程没起来）→ 改框架
> **model**（模型不会写）→ 换模型

`placeholder` 卡在中间：它确实该记在模型头上（模型没写），但"换模型"也不是答案。camp-g 的 r31 是反证——同一个模型、同一个项目，首轮回 `...`（3 字符），二轮只要一个核心函数，交出 1236 字符且编译通过。**能力没变，任务形状变了，结果就变了。**

所以归责要分三类，第三类叫 **task-shape**：

| 归责 | 判据 | 修法 |
| --- | --- | --- |
| framework | steps=0 / 取数非 200 / 端口被占 | 修流程 |
| model | 换粒度、换提示词后**依然**写不出 | 换模型（§2） |
| **task-shape** | 大任务失败、同一能力在小任务上成功 | **切粒度**（本项目的 D4i 分解、§8） |

区分 model 和 task-shape 只需要一个实验：**把同一个失败任务拆小重跑一次**。写不出来 → model；写出来了 → task-shape。这也是为什么 A.6 那个两轮闭环值得做——它不是"提高成功率"的补丁，它是**归责分辨器**。

按这个尺子重新排，下一刀的顺序变了：

1. **task-shape**（113 条占位符 + 26 条没写代码 + 22 条玩具代码，合计约 22%）——不是去调语法，是给 P10 / P9 / P6 这类"整包交付"任务加默认拆解。
2. **framework**（15 条 `unverified` + 11 条超时）——取数不全与 600s 阈值。
3. **model**（Rust 17 条语法错）——真语法问题，但只在 rust 上，而 rust 不是当前主战场。

一句话：**先别修语法，先别换模型，先把任务切小。** 从 A.1 到 A.10，靶心先指向"框架"，再指向"提示词"，再指向"语法"，现在指向"任务形状"——每一次都是尺子变准一点，靶心就往后退一层。这也正是为什么 A.6 那个闭环里最贵的一环是"量"，不是"修"。
