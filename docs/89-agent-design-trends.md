# 89 · Agent 设计趋势与本项目对照：从「能管住」到「会变好」

> 一句话：**趋势不是拿来追的，是拿来当镜子照的。**
> 这份文档把当下 Agent 工程的几条主线摊开，逐条对照本项目现状打分，然后只挑三件"便宜且收益大"的事动手。
> 前置文档：`88-self-evolution-loop.md`（闭环与尺子）。本篇讲方向，88 讲纪律。没有 88 的尺子，本篇全是空谈。

## 0. 趋势判断：三条主线，一条暗线

把近一年的 Agent 工程实践摊开，能落到地上的趋势集中在三处，另有一条贯穿它们的暗线。

| 主线 | 核心变化 | 一句话本质 |
| --- | --- | --- |
| **异构化** | 从"一个模型打所有活"到"按认知功能分层配模型" | 让 2B 做它擅长的（感知、试错），让大模型只在关键处出手 |
| **并行化** | 从"串行走完一步再走下一步"到"fan-out 探索、单点收敛" | 探索可以无限并行，**写入必须过一道闸门** |
| **可验证化** | 从"生成即交付"到"生成-验证-修订（G-V-R）" | 生成的答案不算答案，**被独立验过的才算** |

那条暗线是**预测**。前三条都把系统变复杂了，复杂度一上来，最稀缺的资源就从"模型能力"变成"时间与算力的预算分配"。谁能事先估出"这件事大概要花多久、值不值得做"，谁才能在同等算力下走更远。

### 一个反直觉的判断

这四条里，**可验证化是唯一能立刻见效的**，异构化是最后才该做的。理由很朴素：可验证化是把已有能力用好，异构化是买新能力。买之前先用好手头的——否则你连"新模型到底有没有帮忙"都量不出来。

## 1. 照镜子：八维对照打分

### 1.1 打分表

评分口径（5 分制，只标整数，避免"3.5 分"式的自我安慰）：

- **5** 有实现、有度量、有回归保护
- **4** 有实现、有度量，缺自动回归
- **3** 有实现，无明显度量
- **2** 部分实现或仅有设计
- **1** 基本没有

| # | 维度 | 得分 | 依据（本项目真实状况） | 缺口 |
| --- | --- | --- | --- | --- |
| 1 | **可观测性** | **5** | `soak_project` 每轮落 jsonl、`judge_evidence` 支撑事后重放、`evolve --buckets` 能把失败归到根因桶 | 无，这是最强项 |
| 2 | **治理与安全** | **4** | 26 道门禁、负向演练 8/8、端口段体检 + `pick_port_block` 自动避让 | 缺运行时策略（准入/限流/预算）动态化 |
| 3 | **工具与行动** | **4** | 多 agent 能起进程、打 HTTP、写文件、抽代码、跑编译器 | 工具返回缺结构化契约，worker 常把"我猜"当"我看到" |
| 4 | **多智能体协作** | **3** | 多 agent 命中 99.3%、交接 441 次，能跑通分工 | 交接靠自然语言，缺结构化 payload；无冲突消解 |
| 5 | **推理与规划** | **2** | 有任务分解，能拆子任务 | 无预测、无中途目标复核、超时阈值是拍脑袋定的 |
| 6 | **记忆与知识** | **2** | 有长期记忆目录（gotcha / knowledge / workflow / user.*） | 缺检索、缺去重、缺冲突消解、缺时间衰减 |
| 7 | **自适应性** | **2** | 88 号闭环已能"度量 → 修 bug" | 只覆盖代码缺陷，不含策略自适应（超时/并发/token 预算） |
| 8 | **多模态** | **1** | 基本无 | 全链路文本 |

### 1.2 结论：一句话定位

> **这是一个"能管住"的系统，还不是一个"会自己变好"的系统。**

强项集中在「看得见」和「管得住」——可观测性 5 分、治理 4 分。这两项恰恰是大多数 Agent 项目最弱的地方，值得守住。
弱项集中在「想得远」和「记得住」——规划 2 分、记忆 2 分、自适应 2 分。这三项是系统从"能干活"往"越干越省"跃迁的门槛。

### 1.3 换个视角看：认知功能映射

八维是按工程切面切的，容易看不出病根。换成认知功能再看一遍，问题会清楚很多。

| 认知功能 | 对应维度 | 得分 | 判断 |
| --- | --- | --- | --- |
| 感知 | 多模态、输入解析 | 1–2 | 最弱，但对本项目不致命（任务几乎全是文本） |
| 认知 | 推理与规划 | 2 | **真正的瓶颈** |
| 行动 | 工具与行动 | 4 | 够用 |
| 记忆 | 记忆与知识 | 2 | **第二瓶颈**，且与认知耦合（记得住才规划得准） |
| 元认知 | 可观测性 + 治理 + 自适应 | 4 | **超配**，是差异化 |

这张表里最值得注意的反差是：**元认知是超配的，认知与记忆是欠配的。**

通俗说：这个系统很擅长"事后检查自己做得对不对"（26 道门禁、失败分桶、代际判定），但不太擅长"事中想清楚该怎么做"（无预测、无复核、无记忆检索）。

这个结构其实很罕见——大部分项目反过来：想得多、查得少。所以我们手上的资产不是浪费，而是一个**已经装好的显微镜，等着拿去看更细的东西**。方向不该是"再加强治理"，而是"把治理省下来的信任，花在认知与记忆上"。

## 2. 异构化：按认知功能配模型

### 2.1 现状的问题

当前是**单模型打所有活**：`minicpm5-2b:f16` 既要做任务分解，又要写 Rust，还要自检。这是最大的架构性浪费——用一个只会写短文的小模型去干编译器级别的活，结果必然是 `syntax-error` 占 24.8%。

88 号文档里的失败分桶其实已经给出了分层依据：

| 失败桶 | 指向的能力 | 该由谁干 |
| --- | --- | --- |
| `no-code-at-all`（13.1%） | 理解任务 | 感知层，小模型够 |
| `syntax-error`（24.8%） | 写出合法代码 | 认知/行动层，需要更强模型 |
| `not-delivered`（2.1%） | 遵循格式 | 感知层 |
| `timeout-no-output`（3.4%） | 吞吐 | 与模型大小强相关 |

四类失败指向**完全不同的能力层级**，用同一个模型去打，等于把四种病当一种治。

### 2.2 分层方案

| 层 | 职责 | 建议规格 | 判断理由 |
| --- | --- | --- | --- |
| **感知层** | 任务分类、格式抽取、路由、快筛 | 2B（现行模型） | 高频、低难度、失败代价低，越便宜越好 |
| **认知层** | 规划、分解、目标复核、仲裁 | 14B 级 | 调用次数少但错一次全盘歪，值得上大模型 |
| **行动层** | 写代码、改代码 | 30B 级 | 直接决定 `syntax-error` 与编译率 |
| **裁判层** | 判分、归因 | **保持确定性代码** | 绝不能用 LLM 当裁判（见 88 号 §5.2 假绿事故） |

最后一行是硬约束，不是建议。**裁判必须是确定性的。** 一旦让模型判模型，尺子就软了，前面所有度量全部作废。

### 2.3 一个必须记住的反例：DeepSeek 不做模型异构

2026-10-31 DeepSeek Harness 团队公开的《Super-agent 设计探索》里，原型 `dsh-superagent-prototype`（MIT）走的是**单模型强 + 系统层调度**：Router 与 Worker 用同一类模型，异构体现在**角色与上下文**，不在模型权重。

这说明异构化不是教条。判断条件很清晰：

- **模型足够强时**：异构的收益会被调度开销吃掉（多一次转手、多一次上下文重建），不如把调度做好；
- **算力受限时**（本机纯 CPU、单发约 5 tok/s）：异构是唯一能同时满足"成本可接受"与"关键步骤质量"的路。

我们现在处在后者。所以异构对本项目成立，但理由不是"趋势如此"，而是"这台机器的算力逼的"。一旦上到 GX10 集群（384GB 统一内存），这个结论要重新评估——**记在这里，免得将来把临时手段当信仰。**

### 2.4 怎么验证分层真有用

不能靠感觉。用现成测试台做三组对照，同一个 `--suite py`、同一批项目、同一判据：

| 组 | 配置 | 预期 | 若不符说明什么 |
| --- | --- | --- | --- |
| A（基线） | 全 2B | 达交付 ~55%、syntax-error ~25% | —— |
| B | 2B 感知 + 14B 认知 + 30B 行动 | 达交付 ↑、syntax-error ↓ | 分层无收益 → 瓶颈不在模型而在提示与校验 |
| C | 全 30B | 质量最好但成本最高 | 若 C 与 B 接近，说明感知层用小模型是对的 |

判据三项：达交付率（Wilson 区间）、**单位交付 token**、P95 耗时。只看第一项会得出"越大越好"的错误结论，因为更大的模型一定更贵，而贵必须换来值得的东西。

## 3. 并行化：探索可以散，写入必须收

### 3.1 趋势本身

主流做法是 **fan-out 探索 + 单点收敛**：多个 worker 各自从不同角度试，谁先跑通谁提交；提交动作串行化，避免互相踩。

### 3.2 我们付过的学费：D4i 端口竞态

门禁 10（D4i）曾经出现过一个极隐蔽的故障：上一轮残留的 `super-agents.exe` 占着 18198 端口，新实例启动时**没有报错**，而是打到了旧实例上。结果是——

> **假红与假绿同源。**

失败的那条其实是旧实例在报错，通过的那条其实是旧实例在应答。检测器本身被污染了，而它显示一切正常。

这个坑的通用教训是：**并行的敌人从来不是并发数，而是共享的可写资源。** 端口、文件、git 索引、Ollama 的推理队列，全都是写入点。

### 3.3 由此得到的设计原则

| 操作类型 | 可否并行 | 闸门 |
| --- | --- | --- |
| 读（读文件、查状态、探测端口） | 无限并行 | 无 |
| 算（推理、分析、试写草稿） | 受算力约束（本机约 2 路） | 无，但要算预算 |
| **写**（占端口、写文件、git 提交、改共享状态） | **必须串行** | 单一写闸：端口租约 + 文件锁 |

落到多 agent 架构上就是：**worker 并行思考，Router 串行提交。** 这恰好和 DeepSeek 的 Router/Worker 分离同构——他们是从调度效率出发，我们是从假红假绿的血坑出发，殊途同归。

### 3.4 落点

给写入类操作加一道"单写闸"：

1. **端口租约**：不是"探测到空闲就用"，而是"申请—占用—释放"三段式，释放失败要能自愈（进程被 kill 时锁要能被回收）。
2. **文件锁**：同一路径的写操作走跨进程文件锁，而不是靠约定"你别写我也别写"。
3. **提交串行**：所有"对外可见的变更"（改代码、改配置、写证据）排队过单一闸门。

判断标准很简单：**如果两个 worker 同时做这件事会互相污染，它就必须进闸门。**

## 4. 记忆：三条路线，先做最土的

### 4.1 三条路线各自的坑

| 路线 | 做法 | 主要缺陷 |
| --- | --- | --- |
| **向量 RAG** | 切块 → 嵌入 → 相似度召回 | 召回不可解释；更新是**追加**不是**修正**，旧结论会和新结论一起被召回，互相打架 |
| **结构化记忆** | 实体/属性/关系，写入时校验 schema | schema 僵化；写入成本高；遇到新类型就得改表 |
| **情景记忆** | 事件流 + 定期反思归纳 | 不做反思就只是日志；做了反思则要防"归纳出错误规律" |

三条路线不是三选一，是**配合**。但配合有顺序，顺序错了会白烧很多工程。

### 4.2 本项目已有的资产（比想象中多）

长期记忆目录现在已经是这个结构：

```
task.gotcha      813 条   踩坑与避坑知识
task.knowledge   461 条   领域事实
task.workflow    508 条   可复用流程
user.knowledge    22 条   用户分享的领域知识
user.narrative     1 条   用户讲述的经历
user.preference  110 条   用户偏好
```

这个分类**天然就是"反思归纳"的产物结构**：gotcha = 教训，workflow = 方法，knowledge = 事实。也就是说，情景记忆那条路线最难的一环（"从经历里提炼出什么"）已经有现成的收纳格。

所以结论是反直觉的：**不需要先引入向量库。** 先把"三类记忆 + 一条时间线 + 冲突消解"做扎实，收益远大于换技术栈。

### 4.3 三步走（按性价比排序）

**第一步：让记忆可以被"修正"，而不是只能被"追加"。**

现在的问题不是存不下，是**新旧结论会共存**。举例：某次记下"判分要用 `bool(mark_deliv)`"，后来发现这是 bug 改成三态——如果旧条目不被标记失效，下次召回就可能把错误结论又捞回来。

做法：
- 每条记忆带 `状态`（有效 / 已被取代）与 `supersedes`（取代了哪条）
- 写入前做**冲突检测**：同 domain + 同 point 的旧条目，默认进入"待取代"，而不是并列存在
- 关键：**取代关系要留痕**，可追溯"为什么改主意了"

**第二步：检索先做"土"的。**

不做向量，先做两块：
- **关键词 + 字段过滤**（domain / point / memory_type 都是结构化字段，能精确筛）
- **场景触发**（不是"每次都召回"，而是"遇到 X 类任务才查 Y 类记忆"）

判断标准只有一条：**记忆的价值 = 被召回且改变了行为的次数，不是存储条数。**
813 条 gotcha 如果从不被召回，那就是 813 条死重。所以第一步不是"再多存点"，而是"让它在该出现的时候出现"。

**第三步：反思归纳，但必须带证据。**

从情景流里提炼新条目时，强制携带引用（哪几轮、哪条 jsonl、哪个 sha1）。没有引用的归纳一律降级为"假设"，不进工作记忆。

这一条防的是最难发现的错：**归纳出一条听起来很对、但实际不成立的规律**，然后拿它指导后面几百轮。

### 4.4 顺带一提：记忆与规划是耦合的

记忆 2 分、规划 2 分，看起来是两个坑，其实是一个：**没有记忆的规划只能靠想象。**

规划器要估"这件事大概要多久"，靠的不是推理能力，是历史统计。这就是下一节的入口。

## 5. 预测式多尺度规划

### 5.1 多尺度：三个时间粒度

| 尺度 | 决策内容 | 现状 |
| --- | --- | --- |
| 秒级 | 这一条工具调用要不要发、参数对不对 | 有，但无预算概念 |
| 分钟级 | 这个子任务怎么拆、用哪个模型 | 粗放，靠固定阈值 |
| 小时级 | 这个目标还成不成立、要不要止损 | **完全没有** |

第三行是最大的空白。现在的系统能一门心思跑到 600 秒超时，却从不中途问一句"我还在往对的方向走吗"。

### 5.2 Meta-Thinker：每 N 步插一次目标复核

参照 Meta-Thinker 类做法，在长任务里每 N 步（建议 N=5~8，或每消耗 1/3 预算时）插入一次元认知检查，只问三个问题：

1. **目标还成立吗？**（原始诉求有没有被中途的偏差带跑）
2. **路线还是最优的吗？**（有没有更短的路被忽略了）
3. **要不要止损？**（剩余预算 vs 预估剩余工作量）

关键设计约束：**这个检查必须用便宜的方式做，且必须能给"停止"指令。**
- 用 14B 级（认知层），不用 30B——它只需要判断，不需要生产。
- 输出必须是结构化三选一：`继续` / `改道` / `放弃`，不允许输出长篇分析（长篇分析会把省下的钱花回去）。
- 每任务最多触发 3 次，超出强制走"放弃"分支，防止反复复核本身变成死循环。

### 5.3 用历史数据做预测基线（本项目特有的便宜办法）

这是本项目最容易摘的果子，也是我认为最值得做的一处创意：**评测台攒下的耗时数据，不该只当裁判，还能当预测先验。**

现有历史（145+ 轮真实样本，Python 主线）：

| 指标 | 数值 |
| --- | --- |
| 耗时 P50 | 69.5s |
| 耗时 P95 | 174.7s |
| 单发吞吐 | 约 5 tok/s（纯 CPU） |

由此可以立刻得到一个修正：**`--task-timeout 600s` 是拍脑袋的。**

按 P95 = 174.7s 计算，600s 相当于 P95 的 3.4 倍。这个阈值把大量"慢但会成功"的轮次记成了 `timeout`，直接污染了失败分桶——88 号 §8 里"4 路并行 2 路吃满 600s"其实就是这个错的直接后果。

正确做法是**让阈值由数据决定**：

```
合理超时 ≈ P95(同类任务) × k    （k 取 1.5~2.0）
```

而且 `P95` 应当**分桶查表**，不是全局一个数：

| 维度 | 为什么要分 |
| --- | --- |
| 语言 | Rust 编译成本远高于 Python，混在一起算没有意义 |
| 项目类型 | 涉及并发/中间件的任务天然更慢 |
| 第几轮 | 冷启动的第一轮明显慢于后续 |

落成一个查询表 `(语言, 项目类别, 轮次区间) → (P50, P95, 样本数)`，规划时先查表：

- 预估耗时 > 预算 × 2 → **直接拒绝或降级**（换更小的任务），而不是硬跑到超时；
- 预估耗时在预算内 → 正常执行；
- 实际耗时 > 预估 P95 × 2 → 触发 5.2 的目标复核。

这样规划、预算、止损三件事被同一份数据串起来了。**评测台从此不只是裁判，还是规划器的先验。**

### 5.4 注意：预测会自我实现

一个必须提前写下的警告：如果用预测值去设定超时，那么"预测得不准"会被机制放大成"确实做不完"。所以预测表要**定期用新批次重算**，且保留一部分"不设预测限制"的对照轮次，用来检验预测是否开始偏离现实。

## 6. 可验证化：G-V-R 与 Skills 沉淀

### 6.1 G-V-R 三要点

生成-验证-修订（Generate-Verify-Revise）看起来简单，落地有三个硬要求，缺一个就退化成"生成-自我表扬"：

| 要点 | 要求 | 违反的后果 |
| --- | --- | --- |
| **校验者独立** | 验证不能用生成它的同一个上下文 | 上下文里已经有"我刚写的代码很好"的倾向，验证会变成确认偏误 |
| **有轮次上限** | 最多 N 轮（建议 2~3） | 生成与修订互相拉扯，震荡不收敛，烧光预算 |
| **有客观锚点** | 校验依据必须是确定性的：`compile()` / `rustc` / 测试 / schema 校验 | 靠 LLM 自评 = 软尺子，回到 88 号 §5.2 的假绿事故 |

### 6.2 本项目的缺口：校验器装在了判分侧，不在运行时

现状：`compile_check` 已经有了，而且做得很干净（Python 用 `compile()`、Rust 用 `rustc --edition 2021 --emit=metadata`），但它**只在判分时跑**——也就是"事后量"。

该做的是把它**前移进执行循环**：worker 交代码 → 立刻本机编译 → 不过就把编译器原始报错回灌给 worker 重写（最多 2 轮）→ 还不过才算失败。

这个改动的性价比极高，理由：
- 编译器报错是**最便宜也最精确的反馈**，比让 LLM 自己找错便宜一个数量级；
- 直接打 `syntax-error` 那 24.8% 的桶；
- 复用已有代码，不需要新能力。

同时要立一条规矩：**回灌给 worker 的必须是编译器原文**，不能是"你的代码有语法错误，请检查"这种转述。转述会丢掉行号与具体原因，等于让模型从零猜。

### 6.3 Skills 沉淀：把成功路径固化

趋势上，成功的 Agent 系统都会把"反复用到的解法"从提示词里抽出来，变成可复用单元（本项目的 skills 机制、Claude 的 Skills、各家叫法不同）。

判据只有一条，且必须可量化：

> **同一类任务第二次做时，token 是否下降？**

不降就是没沉淀成功——只是把提示词换了个地方存放。这条判据要写进度量，否则"沉淀"会变成"堆文档"。

## 7. DeepSeek Super-agent 拆解

来源：2026-10-31 DeepSeek Harness 团队《Super-agent 设计探索：迈向更自主的 Agent 系统》，原型 `dsh-superagent-prototype`（MIT 开源）。

### 7.1 架构：Router + Worker

| 角色 | 职责 | 关键设计 |
| --- | --- | --- |
| **Router** | 常驻全局协调，接收群聊 / GitHub / 邮件等事件 | **只分派，不执行** |
| **Worker** | 独立上下文，并行做问题复现 / 代码审查 / 功能开发 | 可再调 Subagent |

一个很实用的细节：**Worker 接手任务后可以直接订阅后续消息**，不必每条都经 Router 转发。这减少了 Router 的转发开销，也让 Worker 能拿到连续上下文。

→ 对我们的启示：多 agent 交接现在靠自然语言，损耗大。让接手方**直接订阅**后续相关输入，比"再描述一遍背景"便宜得多。

### 7.2 存算分离与自愈

| 机制 | 做法 | 解决的问题 |
| --- | --- | --- |
| 存算分离 | 执行循环在云端，会话状态入库，本地只留轻量 daemon | 长任务不怕客户端断线 |
| **Watchdog** | 独立进程检测"无效循环"并尝试修复 | 死循环不是靠超时掐掉，而是被识别出来 |
| 异步 ReAct Loop | 执行耗时任务时仍能响应新指令 | 阻塞式执行会让系统"失联" |

→ 对我们的启示：**Watchdog 这个角色我们现在缺。** 眼下"卡住"只能靠 600s 超时兜底——这是最粗暴的方式（把"慢"和"死"混为一谈）。该有一个独立观察者，用**行为特征**（连续 N 步无进展、同一工具重复调用、输出长度趋零）判"无效循环"，而不是等时钟。

### 7.3 主动性与过滤

- **事件驱动 + 两级过滤**：程序规则快筛（便宜、可解释）→ 大模型慢判（贵、需要理解）。绝大多数事件在快筛层就被丢掉。
- **"静默复现并修复"**：确认问题真实存在、且找到简单修法，才提交；否则保持沉默。这条策略的价值是**压制噪音**——一个总在说话的 Agent 会很快被忽略。

→ 对我们的启示：这条和 4.3 的"检索先做土的"是同一个道理。**便宜的过滤在前，贵的判断在后**，顺序反了就是烧钱。

### 7.4 实测数据（值得记下的几个数）

负载设定：300 条消息、约 20 个工作请求。

| 指标 | 数值 |
| --- | --- |
| 半数任务完成时间 | 12.4 分钟 |
| 95% 任务完成时间 | 15.7 分钟 |
| 单会话子 agent 基准 P95 | 29.5 分钟（**且未调用子 agent**） |

最后一行的意思很值得玩味：在他们的基准里，**没调用子 agent 的简单会话反而 P95 更长**（29.5 分钟 > 15.7 分钟）。说明子 agent 不是开销，是**并行度来源**——分工把长尾削掉了。

压力测试：事件频率 1 → 40 条/分钟

| 指标 | 1/分钟 | 40/分钟 | 解读 |
| --- | --- | --- | --- |
| Router 批大小 | 1.0 | 2.8 | 自动攒批，说明批处理是天然的自适应 |
| 请求延迟 | 2.5s | 3.9s | 延迟涨幅远小于事件涨幅 → 系统有余量 |
| Router 决策数 | 基线 | +30% | 决策数没有线性爆炸，说明过滤有效 |
| 缓存 token | 23.23M | 31.77M | 成本随负载涨，但没失控 |

→ 最值得学的一点：**批大小随负载自适应（1.0 → 2.8）**。我们现在的并发是硬编码的（"2 路"是实测出来的经验值），完全可以改成按队列深度与推理队列状态自适应。

## 8. 落点排序：先做最便宜的

按"改动成本 ÷ 收益"排序，不按"看起来高级"排序。

| 序 | 动作 | 成本 | 直接收益 | 依赖 |
| --- | --- | --- | --- | --- |
| 1 | **超时阈值数据驱动**（P95 × k，分桶查表） | 极低（改配置 + 加查表） | 立刻减少假 `timeout`，失败分桶变干净 | 无，历史数据已有 |
| 2 | **校验前移**（把 `compile_check` 放进执行循环） | 低（复用已有代码） | 原估计打 `syntax-error` 24.8% 的桶；**实测仅 11 条**，见附录 A | 无，但须先修抽取器 |
| 3 | **记忆冲突消解**（状态 + supersedes + 取代留痕） | 中（动数据结构） | 让 813 条 gotcha 从死重变成可用的判断依据 | 无 |
| 4 | **单写闸**（端口租约 + 文件锁 + 提交串行） | 中 | 根治假红假绿，为真并行铺路 | 1、2 之后 |
| 5 | **Meta-Thinker**（每 N 步目标复核，14B） | 中高（需接第二个模型） | 小时级止损能力从 0 到 1 | 需要 14B 可用 |
| 6 | **多模型异构分层** | 高（模型下载 + 内存评估 + 三组对照长跑） | 质量与成本的帕累托改善 | 必须先有 1–5 的干净尺子 |

第 1、2 项本周就能做完，且都能靠现有数据量化效果。第 6 项必须最后做——**在没有干净尺子之前引入新变量，你永远说不清变化是谁带来的。**

## 9. 一页纸结论

1. **定位**：本项目是"能管住"的系统（可观测 5、治理 4），还不是"会变好"的系统（规划 2、记忆 2、自适应 2）。元认知超配，认知与记忆欠配。
2. **最该做的不是加强治理，而是把治理换来的信任花在认知与记忆上。**
3. **异构化成立但只是因为算力受限**，上了 GX10 集群要重估。裁判永远不能用 LLM。
4. **并行的敌人是共享可写资源**，不是并发数。探索无限并行，写入单一闸门。
5. **记忆先做"土"的**：能修正 > 能检索 > 能归纳。判断标准是"被召回且改变行为的次数"，不是存储条数。
6. **预测是暗线**。评测台的数据应当反哺规划器：超时阈值、是否拆解、要不要止损，全部由历史分布决定，而不是拍脑袋。
7. **可验证化最便宜，但要先把锚点钉牢**：编译器已经在手边，可锚点上系的是"抽取器抽到的文本"。抽错了，锚点就是假的，而它仍会自信地报成功——35 条 `'...'` 就是这么混过编译率的（附录 A）。先修抽取，再谈前移。
8. **批量自适应**（DeepSeek 的 1.0 → 2.8）比硬编码并发数优雅得多，值得抄。

> 最后一句留给纪律：趋势里最容易被误用的词是"更自主"。
> 自主的前提是**能验证**；不能验证的自主，只是把错误做得更快。

## 附录 A：写作当天的实证——35 条假绿的解剖

这篇文档正文写完后，当晚给判分器补了一刀（占位符识别 + 语言猜错隔离）。
结果值得单独记一节，因为它把正文里几条抽象原则变成了带血的数字。

### A.1 发生了什么

对 233 条"有完整证据"的样本按当前判据重算，**48 条翻案**：

| 方向 | 条数 | 原文 | 说明 |
| --- | --- | --- | --- |
| `True → None` | **35** | `'...'` | Python 里 `...` 是合法的 Ellipsis 表达式，`compile("...")` **成功** |
| `False → None` | 13 | `<code here>`、`<你的代码>`、`... (your full code here) ...` | 送去编译必然 SyntaxError |

也就是说：过去报表里那 35 条"编译通过"，代码原文只有三个点。

### A.2 分桶因此整体改写

| 桶 | 修正前 | 修正后 |
| --- | --- | --- |
| `syntax-error` | 56 条（第一大桶） | **11 条**（其中 rust 8、python 3） |
| `placeholder-instead-of-code` | 不存在 | **48 条**（占可复验子集 18.2%，第一大桶） |
| `legacy-unverified` | 不存在 | 33 条（旧口径残留、无证据可复算，不参与决策） |

编译口径同时纠偏：**275/324（84.9%）**，分母只含"可判定轮"；
其中证据在手、能被当前尺子复算的 **可复验子集 264 轮**，跨代比较只认这一档。

### A.3 三条教训

**一、假绿比假红更危险。**

假红会让数字难看，人不爽，于是去查；假绿会让数字好看，人满意，于是什么都不会发生。
35 条假绿静悄悄躺了很多轮，一直在替"编译通过率"抬轿子，没有任何人会觉得它有问题。

这直接对应正文 §6.1 的第三要点：**验证必须有客观锚点**。
我们以为自己有（编译器），但锚点上系着的是"抽取器抽到的文本"——
抽取器抽错了，锚点就是假的，而它仍然会给出自信的成功。

**二、假红和假绿永远同源。**

它们的根都不是"编译逻辑错"，而是"抽取器抽到了非代码内容"。
修一个判据，两个方向同时收敛——这就是为什么正文 §8 里"校验前移"的收益被高估了：
在抽取器不可靠的前提下，把编译校验挪到执行循环里，只会让假绿更早发生。

**顺序应该是：先保证"验的是真东西"，再谈"什么时候验"。**

**三、靶心必须由尺子回答，不能由直觉回答。**

修正后的靶心完全变了：

- 旧桶指向"提示词里的语法约束不够"→ 会去调提示词格式要求；
- 新桶指向"**模型压根没写代码，只吐了模板占位符**"→ 要硬性禁止占位符、给反例、必要时判失败重来。

如果只看旧桶就开干，会花一周去修一个只剩 11 条的问题，而真正占 18.2% 的问题一动没动。

> 这是 88 号"下一次修改必须由尺子指出来"那条纪律的第一次真实兑现。
> 尺子本身也会错——所以它必须可复算、可翻案、留证据。留证据不是为了审计，
> 是为了**允许自己推翻自己**。
