# 计划模板（planner-agent 领域底座）

用途：`wbs` / `risk-register` / `milestone-plan` 技能的执行判据。
核心：计划的唯一价值是**让明天该做什么没有歧义**。做不到这点的计划只是把任务换了个说法。

---

## 1. WBS 拆解规则

- **按交付物拆，不按动作拆**：写"可运行的登录接口（含测试）"，不写"写代码"。
- **叶子标准（MECE 之外的三条硬约束）**：
  1. 一个叶子 ≤ 2 人日（超过就继续拆）；
  2. 有唯一负责人（不写"团队"）；
  3. 有可验证的完成判据（能跑的命令、能看的结果）。
- **层级最多 4 层**，再深就是没想清楚，而不是拆得细。
- 拆完检查：所有叶子加起来是否**恰好**等于父项范围——有超出（范围蔓延）或缺口（漏项）都要回到上一级重拆。

## 2. 依赖与关键路径

- 依赖只记**真实数据流/资源流**（B 需要 A 的产物），不记"习惯上先后"。
- 关键路径 = 最长依赖链。它是唯一值得加人的地方；给非关键路径加人只会增加沟通成本。
- 每段依赖标"硬依赖/软依赖"：硬依赖不能并行，软依赖可以并行但需要额外对齐。
- 存在外部依赖（等待第三方、等待审批）时，**单独列外部等待清单**并给出兜底假设（假设多久能批下来）。

## 3. 里程碑设计

| 要素 | 要求 |
| --- | --- |
| 名称 | 用"能对外交付的东西"命名，不用"阶段一" |
| 判据 | 一条可验证的验收条件（演示/测试通过/上线） |
| 日期 | 具体日期，不写"约""左右" |
| 可逆点 | 这个里程碑后能否撤？撤的代价是什么 |

里程碑间隔建议 1~3 周。超过 3 周的里程碑必然失控，因为期间没有任何人知道进度。

## 4. 风险登记（risk-register）

| 字段 | 填法 |
| --- | --- |
| 风险 | 具体事件，不写"可能有风险" |
| 触发信号 | 什么现象出现说明它正在发生 |
| 概率/影响 | 高/中/低（两个维度分开评，不用乘积糊弄） |
| 应对 | 规避 / 减轻 / 转移 / 接受，四选一 |
| 责任人 | 一个人 |
| 复查日 | 具体日期 |

只登记**前 5 条**真正会改变计划的。列 30 条风险的登记表没人看。

## 5. 排期原则

- 估时用三点估：乐观 / 最可能 / 悲观，取 `(O + 4M + P) / 6`。
- 留缓冲：总工期留 15%~25%，**放在里程碑层，不放在每个任务里**（放任务里必被吃掉）。
- 人力按 70% 可用率折算（会议、沟通、救火）。
- 同一人不得同时承担两个关键路径任务。

## 6. 验收标准编写

一条合格的验收标准必须**可被第三方独立判定**：

- ✗ "性能良好" → ✓ "P95 响应 < 300ms（1000 并发，本机压测）"
- ✗ "文档齐全" → ✓ "README 含安装/启动/接口三项，新人照做能在 30 分钟内跑起来"
- ✗ "代码质量高" → ✓ "clippy 无警告，新增逻辑有测试且覆盖失败路径"

## 7. 交付格式

1. **目标一句话** + 完成判据。
2. **WBS 表**：编号 / 交付物 / 负责人 / 估时 / 依赖 / 完成判据。
3. **关键路径**：列出链条，标出唯一可加速点。
4. **里程碑表**：名称 / 日期 / 判据 / 可逆点。
5. **风险登记**：前 5 条。
6. **需要决策的事**：哪些点需要用户拍板、最晚何时拍板（超期会怎样）。

## 8. 红线

- 不排"看起来合理"的日期。估不出来就写"需先做 2 天技术验证，再定日期"。
- 不把"待定"藏在任务描述里，单独列出待定清单。
- 不承诺资源之外的产能（人手不够就说清"按现有人力，X 必然延后"）。
